# 配音链路技术方案（Convert Video · 第二期）

> 状态：**方案待确认**（门禁：确认后才动手写代码）
> 日期：2026-10-27　分支：`main-convert`　前置：`a51d69c` Convert Video 对话框（UI 已完成，管线未接）
> 本文所有工期为**单人**、不含选型验证；所有未实测的数字都标了「待实测」。

---

## 0. 一页结论

在 Convert Video 对话框里，在「Translate the speech」下面加一行 **「Dub it into that language」**，勾上之后输出文件带**两条音轨**：默认播放的配音轨，和原声轨。

链路八个阶段，顺序固定：

```
字幕链(ASR → 翻译)  →  人声分离  →  说话人分离  →  逐句克隆 TTS  →  时长对齐  →  混音  →  画面三阶段  →  mux(两条音轨)
```

- **工期：23–33 人天**（不含选型验证）。拆解见 §7。
- **先花 2–3 天做选型验证**（§6）。五项验证里任一不过，方案要改——最可能是退回「固定音色」，能砍掉约 7–10 人天和一条法律风险。
- **两个门禁**：① 本方案确认；② 选型验证五项通过。
- **一条硬约束**：不预置任何演员音色库，参考音频只能来自用户自己的文件，并需显式权利确认（§10.3）。
- **一个新加的死约束（2026-10-27 实测）**：Windows + AMD 上，PyTorch 系 TTS **没有可用的 GPU 路径**（CUDA 无 / ROCm 无 Windows / DirectML 四层不兼容），CPU 上 F5-TTS 的 RTF 是 **17.5×**，2 小时片子约 **14 小时**。整片配音在当前技术栈下不可交付，见 §13。

## 2. 目标与非目标

### 2.1 目标

1. 一部外语片，一次转换产出一个**中文（或其它目标语言）配音 + 保留原声**的文件。
2. 配音听起来是「原演员在说目标语言」，而不是一个陌生人的声音。
3. 原片的背景音（配乐、音效）保留。
4. 台词与画面**不脱同步**，宁可语速略快也不对不上口型。
5. 失败必须可观测、可解释：哪一段错了、哪一句压缩了多少，日志要写。

### 2.2 非目标（这一期明确不做）

| 不做 | 理由 |
|---|---|
| 口型对齐（lip sync / 换脸级对口型） | 另一个数量级的工程与法律风险，与「配音」是两件事 |
| 多人同时说话的分轨 | 分离技术做不到；重叠对白按「取能量最大的一路」处理并记日志 |
| 预置演员音色库 | 法律红线（§10.3） |
| 实时配音（播放时） | 这是离线转换功能；播放路径不碰 |
| 配音的语气表演（生气/耳语） | 克隆模型的能力边界，先保「像谁」再谈「像不像在演」 |
| 不参考音频的「纯文本 TTS」 | 与「克隆原演员」的目标冲突，只作为兜底开关存在（§4 D2） |

## 3. 链路设计

### 3.1 顺序与理由

| # | 阶段 | 输入 | 输出 | 失败代价 |
|---|---|---|---|---|
| 1 | ASR | 源音轨（按片段 trim） | 逐句文本 + 时间轴 | 2–6 分钟 |
| 2 | 翻译 | 逐句文本 | 目标语言逐句文本 | 2–3 分钟 |
| 3 | 人声分离 | 源音轨 | 背景轨 + 人声轨 | 3–8 分钟（待实测） |
| 4 | 说话人分离 | 人声轨 + 逐句时间轴 | 每句 → 角色 ID | 2–5 分钟（待实测） |
| 5 | 克隆 TTS | 每角色参考音频 + 逐句译文 | 逐句配音波形 | **20–60 分钟（待实测，最大头）** |
| 6 | 时长对齐 | 逐句波形 + 原时间轴 | 对齐后的配音轨 | 秒级 |
| 7 | 混音 | 背景轨 + 配音轨 | 成品配音轨（48 kHz 立体声） | 秒级 |
| 8 | 画面三阶段 + mux | 视频 + 原文件 + 配音轨 | 成品容器 | 画面阶段是大头 |

顺序的三条理由：

1. **便宜的先失败。** 1–4 加起来十几分钟，5 开始才是小时级。字幕链放在最前，配音链紧跟其后，画面渲染排在最后——这一点在第一期已经确立，这里不变。
2. **配音必须全部就绪才能进 mux。** mux 是唯一一次写目标文件，配音轨是它的第三个输入。
3. **画面阶段与配音链互不依赖**，理论上可以并行；**但本期不并行**：两者都吃 GPU（whisper-FFX / 分离模型 / TTS 抢同一块卡），并行会让画面阶段掉速且难以归因。串行，进度好表达。

### 3.2 失败语义

**任一阶段失败 → 整单失败，清 scratch，不产出半成品。** 配音半成品（一半中文一半静音）比没有更难排查。

唯一的例外是**降级**，且必须显式：见 §4 D2 的「单一音色兜底」——那是用户在那个开关上选的，不是系统偷偷降级。

### 3.3 取消

沿用现有 stop_token 语义，追加两条：

- TTS / 分离 / diarization 若是外部进程，一律进 kill-on-close job object（和 ffmpeg / llama-server 同样的处理）。
- 取消后必须确认子进程真的退出——这个坑项目里踩过（whisper 16 线程满载残留），验收标准里有一条专门测它（§9.6）。

## 4. 关键设计决策

| # | 决策 | 理由 | 可推翻性 |
|---|---|---|---|
| **D1** | 配音轨 = 人声分离后的背景 + 生成的配音，混成一条 | 纯配音轨会让整片没有配乐和音效；原音轨压低当背景会和人声重叠。观感优先 | 可退回「纯配音轨 + 原声保留」，省 3–5 人天 |
| **D2** | 每个角色一个音色（diarization），对话框给「Voices: 每个角色 / 单一音色」兜底开关 | 用户明确要求「像原演员」；但 diarization 在影视素材上准确率未知，分错时（主角声音说反派台词）必须有退路 | 兜底开关默认「每个角色」，用户可切 |
| **D3** | 参考音频自动选：每角色取「该角色最长的一段、背景最静」的区间；日志写明取自哪个时间码 | 零样本克隆需要干净的单人参考；错误必须可解释、可手动干预 | 后续可加「手动指定时间段」输入框 |
| **D4** | 时长对齐（**已按实测改写两次**）：**全局基准语速 ×1.15**（XTTS 每音节 154 ms，原片 135 ms，慢 14%，1.15 正好补齐）→ 逐句只做 ≤1.25 的微调 → 仍超的句子用**字数预算重译**（预算 = 窗口 × 5.0 字） | 实测：7/7 句在单一 1.15 下装进窗口（最大 93%），**没有一句需要单独提速**；停顿不是原因（最长 0.18 s）；×1.55 人耳判为“急”；`length_penalty` 无效 | 1.15 与 1.25 都可用真素材再标定；换引擎必须重新标这两个数 |
| **D5** | 配音语言是**独立**的下拉，条目比字幕的 17 种少很多 | 文本翻译 17 种 ≠ TTS 会 17 种。多语种 TTS 稳的通常 5–8 种。两个列表混在一起会骗人 | 最终列表等 V1 验证结果定（§6） |
| **D6** | 输出两条音轨：**配音轨做默认**，原声轨保留 | 用户要的就是配音；原声留着，想听背景/原声的人切一下就有 | 默认轨可改成原声 |
| **D7** | mux 加第三个输入（配音轨）+ 一条 `-map` + 语言元数据（`zho`/`jpn`/…） | 复用现有 ffmpeg 参数构建器，改动小（约半天）；不写第二条 mux 实现 | — |
| **D8** | 三个新模型全部 opt-in 附件，标准包里这一行置灰 | 与字幕引擎同一套分发规则（`-IncludeSubtitleEngine` 模式）；体积 4–6 GB，不能塞进默认包 | 用户若接受默认包翻几倍，可改为默认带 |
| **D9** | 不预置任何演员音色库；勾选时需显式确认「你有权使用这段音频的音色」 | 真人声音合成涉及声音权（中国《民法典》参照肖像权保护），公开发布必须站得住 | 不可推翻 |
| **D10** | 配音轨统一 48 kHz / 立体声 / AAC（mp4）或 PCM→AAC（mkv） | 分离输出、TTS 输出、混音输出的采样率各不相同，必须统一到一个工作格式，否则混音阶段会做隐性重采样 | — |
| **D11** | 配音链路带**专名表**（人名/地名/术语），翻译时强制沿用 | 实测：`Celia -> 塞莉亚` 在一次重译里变成 `凯莉`。单句听着都对，但同一个角色在不同句子里被叫成不同名字——时长问题会被听出来，这个不会 | 表从首次翻译产物里抽取，存 `[ConvertVideo] Names` |

## 5. 接口冻结页（本节确认后不许改）

### 5.1 对话框控件

| 控件 | ID | 标签 key | 默认 |
|---|---|---|---|
| 配音语言（下拉，第一行「Do not dub」） | `IDC_CV_DUB` = 7616 | `convert.dub` | 0（不配音） |

> **已落地时改号（2026-10-28）**：7616 在代码里已经是转换进度面板的 Cancel
> （`IDC_CV_PROGRESS_CANCEL`，先于本方案存在，不移动）。配音行顺延为
> **`IDC_CV_DUB` = 7617**，`IDC_CV_VOICES` = 7618、`IDC_CV_DUB_RIGHTS` = 7619。
> 本轮只落 7617（配音行 + 拒绝态 + 引擎探测），音色策略与权利确认待克隆一起做。
| 音色来源（下拉：每个角色 / 单一音色） | `IDC_CV_VOICES` = 7617 | `convert.voices` | 每个角色 |
| 权利确认（勾选框，仅 DUB>0 时出现） | `IDC_CV_DUB_RIGHTS` = 7618 | `convert.dub_rights` | 不勾 |

联动规则：

- `DUB > 0` → 字幕自动抬到「软轨」（配音必然有文本，文本必须有地方去）
- `DUB > 0` 且权利确认未勾 → **Run 置灰**，摘要行显示 `convert.refusal.rights`
- 三个新模型任一缺失 → `IDC_CV_DUB` 置灰，tip 写明缺哪一个

### 5.2 ini `[ConvertVideo]` 新增键

```ini
Dub=zho            ; 空 = 不配音。与 Target 分开：字幕语言与配音语言是两个问题
Voices=per-speaker ; per-speaker | single
DubRights=1        ; 用户确认过的记忆，首次为 0
```

### 5.3 数据结构（新增，冻结）

```cpp
// 配音链路的计划，由 PlanDub 产出。与 ExportPlan 平级，不塞进去：
// 配音是三段新链路，失败语义与 ExportPlan 的拒绝理由完全不同。
struct DubPlan {
    bool valid{};
    DubRefusal refusal{};
    std::string languageCode;   // "zho"/"jpn"/…，配音轨的 ISO 语言码
    std::string languageName;   // 显示用
    bool perSpeaker{true};
    // 参考音频的来源，写进日志让人能复核
    struct VoiceSource { int speakerId{}; double startSeconds{}, endSeconds{}; };
    std::vector<VoiceSource> references;
    uint32_t sentenceCount{};   // TTS 要合成的句数，进度用
};
DubPlan PlanDub(const DubSelection& selection, /* 依赖已有产物 */ ...);

// 一段新链路的请求。三个阶段共用一个形状：进文件、出文件、可取消。
struct DubStageRequest {
    std::filesystem::path source;       // 源音轨或上一步产物
    std::filesystem::path output;       // scratch 里的中间文件
    std::filesystem::path voiceDir;     // 参考音频目录（TTS 用）
    double targetSeconds{};             // 音频总长，进度分母
};
```

### 5.4 进度（Pass N of M）

配音三条链各占一趟，单位是**秒**（不是帧）：

| Pass | `passKey` | 数字含义 |
|---|---|---|
| 1 | `convert.progress.speech` | 已听秒数 / 总秒数 |
| 2 | `convert.progress.translate` | 已译句数 / 总句数 |
| 3 | `convert.progress.separate` | 已处理秒数 / 总秒数 |
| 4 | `convert.progress.speakers` | 已判句数 / 总句数 |
| 5 | `convert.progress.dub` | 已合成句数 / 总句数 |
| 6.. | `export.progress.pass_*` | 沿用画面阶段 |

需要给 `StageExportProgress` 加一个 `const wchar_t* unitKey`（`convert.unit.seconds` / `convert.unit.sentences` / `export.unit.frames`），否则字幕段会显示成 `0 / 0 frames`。

### 5.5 命令行

本期不给 `--render` 加 `--dub`。理由：命令行是批处理入口，配音每片 1 小时以上，批处理的失败恢复没设计过。要加是独立一期。

## 6. 选型验证计划（2–3 天，先做这个）

一段 3–5 分钟**真实素材**（建议 `tears_of_steel_720p.mov` 里挑有对白 + 配乐 + 多角色的段落），跑下面五项。**全部通过才开工。**

| # | 指标 | 方法 | 通过标准 | 不通过怎么办 |
|---|---|---|---|---|
| **V1** | 跨语言音色迁移 | 英文演员音色 → 说中文，人耳 A/B | 听得出「是那个人」，且中文无外国口音 | **退回固定音色**（砍约 7–10 人天 + 法律风险） |
| **V2** | diarization 准确率 | 人工标注 100 句的角色，比对 | 准确率 ≥ 90%，且不出现「主角↔反派互换」 | 关掉每角色模式，只留单一音色 |
| **V3** | 人声分离质量 | 分离后的背景轨人耳听 + 人声残留 | 背景无可闻人声残留，无金属伪影 | 退回「纯配音轨 + 原声保留」（D1 的反向） |
| **V4** | 对齐听感 | 跑完整段，看压缩比例分布 | 需压缩 >15% 的句子 < 10% | 调整阈值 / 换成允许溢出的策略 |
| **V5** | 成本 | 2 小时片端到端计时 | 可接受（暂定 < 90 分钟 TTS） | 决定是否只在预览片段开放配音 |

**V1 必须是第一个跑的。** 它决定了后面 20 人天有没有意义。

> **已跑（2026-10-27）**：结果与修订见 [`dubbing-validation-results.md`](dubbing-validation-results.md)。
> V1/V3/V4 通过、V2 差 1% 到门槛（失败点为经处理的声音）。**§4-D4 已按实测改写**：
> 从"合成后压缩"改成"合成时按窗口设语速"，`speed` 实测不改音高、7/7 句可装进窗口。

## 8. 风险清单

| # | 风险 | 影响 | 处理 |
|---|---|---|---|
| **R1** | 跨语言音色迁移失败（外国口音的中文） | 整个功能的核心卖点塌掉 | V1 门禁；不过就退回固定音色 |
| **R2** | diarization 在影视素材上错得离谱 | 「主角声音说反派台词」，比统一音色更难听 | V2 门禁；兜底开关随时能退回单一音色 |
| **R3** | 真人声音合成的授权问题 | 公开发布站不住 | 不预置音色库 + 显式权利确认（D9）；不做「一键克隆任意电影」的营销表述 |
| **R4** | Python sidecar 的取消/崩溃/残留 | 界面显示已取消，后台仍占满 CPU/GPU | kill-on-close job object + 取消后查进程；§9.6 专项验收 |
| **R5** | 体积 4–6 GB | 发布包大一个数量级，下载门槛抬高 | opt-in 附件（D8）；单独决定是否默认带 |
| **R6** | TTS 是最大时间头（2 小时片可能 30–60 分钟） | 用户点了之后以为卡死 | §5.4 的句数进度 + ETA；配合「仅转换片段」先试 |
| **R7** | 三段新链路 × 三个模型 = 组合爆炸的失败模式 | 排查困难 | 每段独立 scratch 产物 + 每段日志带明确阶段名；失败一定说清是哪一段 |
| **R8** | GPU 抢占（whisper/分离/TTS/画面阶段抢同一块卡） | 画面阶段掉速、时序不稳 | 串行执行，本期不并行（§3.1 理由 3） |

## 9. 验收标准（可判定）

## 13. 2026-10-27 的验证结论（覆盖本文的工期与可行性）

详见 [`dubbing-validation-results.md`](dubbing-validation-results.md)。三条结论直接影响本文：

| # | 结论 | 影响 |
|---|---|---|
| 1 | 链路可行：分离（背景零漏音）、diarization（纯度 8/9）、跨语言克隆（同人 0.32 / 异人 0.05）、时长可控（7/7 装进窗口） | §7 的 23–33 人天里，2/3/5 项的风险大幅下降 |
| 2 | **引擎换成了 F5-TTS**：XTTS 的 `speed` 改 `length_scale` 会伤音色（人耳判"仓鼠音"），F5 默认语速已够快，不需要提速 | §4-D4 的"全局 1.15"被 F5 消掉；但 F5 权重许可有商用限制（待核实） |
| 3 | **GPU 跑不了**（见下），CPU 上 RTF 17.5×，整片 14 小时 | **§7 的工期不再成立**：不是"能不能做完"，是"做完了用户也用不了" |

### 13.1 GPU 死约束（亲手验过，四层）

- `torch.cuda.is_available()` = False（NVIDIA 专属）；ROCm 不上 Windows 消费卡。
- 唯一路径 DirectML：① 只能配 torch 2.4.1，而 transformers 5.x 拒绝在 <2.6 启用 torch；
  ② F5 内部 `"cuda" in device` 不认 device 对象；③ safetensors 不认 `privateuseone`；
  ④ 全绕过之后 `RuntimeError: Cannot set version_counter for inference tensor`。
- **结论**：这不是"优化空间"，是路径不存在。要做整片配音，需要一个能在 AMD 上跑 GPU 的 TTS 运行时
  （Vulkan 或 ONNX+DirectML 的原生实现），那是独立工程，不是本期。

### 13.2 修订后的三个可选范围

| 范围 | 交付时间（2 h 片） | 结论 |
|---|---|---|
| **整片配音** | 约 14 h（TTS）+ 1.5 h（分离） | ❌ 不可交付 |
| **短片段配音**（1–2 分钟预览） | 约 9 min / 30 s 语音 | ✅ 可交付，但产品价值要重新定义 |
| **只做字幕**（不做配音） | 分钟级 | ✅ 现在就能交付，链路已验证 |

**建议**：本期收敛到"字幕"或"短片段配音预览"。§7 的 23–33 人天按整片配音估的，

### 13.3 引擎定案（2026-10-27 最终）：XTTS-v2，克隆

## 14. 2026-10-28 实测：引擎换成 Qwen3-TTS 后，§13 的「不可交付」不再成立

§13 的 14 小时/不可交付，是 **F5-TTS + PyTorch** 的量（CPU RTF 17.5×，且 Windows+AMD 无 GPU 路径）。
本仓库自带的 `translation/runtime/llama-tts.exe` 是 **ggml/llama.cpp 的 Qwen3-TTS**，不走 PyTorch，实测：

| 项 | 实测 |
|---|---|
| 输入 | 15 个汉字（`你好，这是一段中文配音的测试。`） |
| 输出 | 4.96 s 语音，24 kHz **单声道** pcm_s16le |
| 耗时 | prompt 0.20 s + 生成 2.36 s + vocoder 1.00 s = **3.56 s** |
| 速度 | **1.39× 实时**（audio time / process time） |

推论：2 小时片按 60~70% 有对白估算，TTS 约 **1~1.4 小时**（不再是 14 小时）。
**§13.2 的「整片配音不可交付」应据此重估**；短片段配音则降到分钟级。

代价与待办：

- 输出是 **24 kHz 单声道**，而 §4-D10 定的工作格式是 48 kHz 立体声 —— 混音阶段必须重采样+上混（不能改 D10，改的是 TTS 之后）。
- 本次是**固定音色**（未传 `--tts-speaker-file`）。克隆要参考音频 + 说话人嵌入，属下一期。
- 单次合成的模型加载时间未计入上表（本次含在 3.56 s 内）；逐句合成若每句重启进程会放大这块，

## 15. Python 调研 → C++ 实现的映射（2026-10-28）

`tools/dubbing` 的六阶段 Python 链已跑通整片（Tears of Steel 734 s / 71 句，

### 已固化进 `src/DubFitPolicy.h`（常量 + 纯函数，PolicyTests 430 钉住）

| 经验（实测） | 落地 |
|---|---|
| 窗口 = `next_start - start`，不是 `end - start`；帽 +1.5 s、地板 0.5 s | `WindowSeconds()` |
| 让步顺序 借静音(≤2.0/留0.15) → atempo(1.25，短窗<1.2 给 1.50) → 重写(≤2 轮) → 报出来 | `ConcessionFor()` / `ShiftFor()` / `TempoCeilingFor()` |
| `REWRITE_ABOVE` 故意 == `MAX_TEMPO`：加速能吸收的绝不去问翻译引擎 | `kRewriteAbove` |
| atempo **下限 0.85**（放慢）：中文比台词短会提前停，原声已挖走只剩音乐 | `kMinTempo` / `ClampTempo(...,allowSlower)` |
| 节奏模型 `秒 = 0.1425×汉字 + 0.665×逗号 + 0.399`（R²0.924 / MAE 0.236） | `kQwen3TtsPace` / `PredictSeconds()` |
| 预检只往「没救」方向用（MAE 0.236 s） | `ReachableSeconds()` / `IsHopelessBeforeSynthesis()` |
| 合成后必须裁静音（−48 dBFS，两端留 40 ms）：不裁则窗口全用来加速静音 | `kTrimSilenceDb` / `kTrimPadSeconds` |
| 音轨语言必须写 B 码 `chi`（写 `zho` 被 mov 静默丢弃） | `TrackLanguageCode()` |
| 母版限幅 `limit=0.794`，**必须 4× 过采样**（44.1k 看不见样点间的峰） | `kPeakLimit` / `kLimitOversample` |
| 电平按 20 ms 块 75 分位（整段 RMS 会推高 3~4.9 dB）；增益夹 ±12 dB | `kLevelBlockSeconds` / `kLevelPercentile` / `kGainClampDb` |
| bed 只在该响处压 −3 dB + 150 ms 斜坡（常数压会让真静场听起来像断音） | `kBackingGain` / `kDuckDb` / `kDuckRampSeconds` |
| 撞车硬上限 1.35（比拟合 1.25 高一档），行间 ≥0.03 s | `kHardTempo` / `kMinGapSeconds` |
| 字幕文本/起止**必须取自配音实际念的行**（曾 13/71 不一致） | `kMinSubtitleHoldSeconds` / `kMaxSubtitleLineUnits` |

### 引擎事实（会改变实现方式，不是调参）

- **llama-tts 没有 speed 参数**（只有 `--temp`）→ XTTS 那套「合成时设语速」不能沿用，
  调速只能事后 atempo。
- **`--temp 0.7` 采样 → 同一句两次时长不同**（实测 1.12 / 1.68 s）→ 超窗集合每轮都变，
  调参要跑 2~3 轮看集合是否收敛；单次合成波动 ±0.72 s，节奏模型只能初筛。
- **输出 24 kHz 单声道**，工作格式 48 kHz 立体声 → 混音前必须重采样 + 上混。
  重采样走 ffmpeg `-resampler soxr -precision 28`，**该选项必须在输出侧**（放输入侧 ffmpeg 非零退出）。

### 还没搬过来的（下一期实现时逐条处理）

1. **ASR 幻觉过滤**：whisper 在音乐段会刷屏（392 段里 373 段是同一句）→
   「每种文本只取首次出现」+ 内容白名单正则（credit / `*...*`）+ 相对能量门槛 `0.03 × 句中位数`。
2. **whisper 的段落时间不可信** → 只信人声轨能量：rough ±0.8 s 内找最长连续语音段，
   已认领区间要屏蔽（两句会抢同一段），找不到语音判幻觉丢弃。
3. **长段重切**：`span > max(3.0, 词数/2.6*1.8)` 的 whisper 行单独重转写，
   只接受 ≥2 行且最长行与原文词重合 ≥0.5 的结果。
4. **翻译层必须留 translategemma**（Granite AST 当翻译不可用：18 句里短句成片崩）。
   且要防三种废输出：答非所问（服务话术正则）、不遵守字数预算（比初稿长就弃用）、

5. **覆盖表** `zh_overrides.json`（null = 整句不配，专治两句共用一段语音）。
6. **术语表** `glossary.json`（译名漂移：Celia 在四种写法间跳）。
7. **响度对齐到集合中位数**，增益夹 ±12 dB（TTS 自身响度差 20 dB）。
8. **没配上中文的行补回原声**，只能逐行补（扫未覆盖语音段会灌进 60 s 英文）。

## 18. 「中英文一起响、中文偏小」的两个根因（2026-10-28 修复）

**症状**（用户实测）：播放成片时英文和中文叠在一起，中文比英文小声。

**根因 1：双轨导出还在垫 bed。** `dub::Plan::bed` 默认 `true`，而 bed 是
`-map 0:a:0` 抽出的**整条原声（含英文人声）**——Python 管线敢加 bed 是因为它先做了人声分离
（`stems_out/no_vocals.wav`），C++ 端口没有分离器。更糟的是 bed 只乘 `kBackingGain = 0.85`
（≈ −1.4 dB），`kDuckDb / kDuckRampSeconds` 这两个常量**只搬进来没实现**，所以英文几乎满电平
压在中文底下。而封装同时又单独保留了原声轨 → 同一个英文在两条轨上都存在。

**根因 2：人声没有绝对电平锚点。** 混音只把每句对齐到「各句电平的中位数」（相对齐平），
中位数本身落在哪完全由引擎决定。实测纯人声母版 peak −7.8 dBFS、对话窗 LUFS −24.9，
比源片（peak −0.2、同窗 −11.1 LUFS）低一大截，限幅器全程没参与。

**修复**：
1. `src/main.cpp`（Convert 路径）与 `tests/DubConvertE2E.cpp` 都显式 `dubPlan.bed=false`；
   `dub::Plan::bed` 默认改为 `false`，注释说明「只有这一轨是文件唯一音轨时才开，且需要 stem 分离」。
2. 新增 `kFillHeadroom / kDialoguePeak(0.5 = −6 dBFS) / kMaxNormalizeGain(4.0)`：
   混音后按**各句峰值的中位数**把中位句顶到 −6 dBFS，超出的交给限幅器。
   ⚠️ 不能按「全局最响一句」对齐：实测 29 句峰值跨度 −20.5 ~ −3.5 dB（17 dB），
   按最响句对齐会让普通句整体低 6 dB（第一版就是这么做的，LUFS 只到 −24.9）。

**验收**：
| 指标 | 修复前（有 bed） | 修复后（纯人声） |
|---|---|---|
| 配音轨 mean / peak | −18.9 / −1.8 dB | −26.1 / **−2.0** dB |
| 对话窗 LUFS（0:10–0:45） | −24.9 | **−18.0** |
| whisper 回听配音轨 | 中英混杂 | **全中文**（唯一拉丁词是专有名词 Celia） |

**遗留（产品取舍，需要你定）**：没有 M&E（音乐/音效）分离，所以纯配音轨在非对白时段是静音，
背景音乐只在原声轨上。要「中文 + 原音乐音效」两全，得在 dub/ 里接一个 stem 分离引擎
（Python 侧用过 demucs 一类），或退回 bed 但必须实现真正的闪避（−12 dB 以上）且接受英文仍隐约可闻。

## 19. 「音色变了」：引擎每句换人（2026-10-28 修复）

**症状**：听感上配音音色不对/不稳定。

**根因**：C++ 端口调 llama-tts 时**没传 `--tts-speaker-file`**。
Python 管线每句都传（`step12_fit_auto.py:256`，参考音来自 `step11_refs_auto.py` 从**分离出的人声**
剪的 10–15 s，按角色一份）。没有这个参数时，`--temp 0.7` 的采样在**每句换一个说话人**——
所以音色逐句漂移，也与片中演员无关。

**修复**（三处）：
1. `dub::Plan::voiceReference` + RunDub 自动选参考：取**最长的一条非标注 cue** 的片源音频 10 s
   （一条 cue = 一个人在说话），`-ac 1 -ar 24000` 后作为 `--tts-speaker-file`，全片统一音色。
   ⚠️ 参考音必须来自**干净连续的人声**：Python 用的是 vocal stem，我们只有混音，所以只能挑单句；
   用带音乐/中途截断的段落会让模型**复读循环**（实测上一轮 fit3 把「好了Celia我们必须按照…」念了 7 遍）。
2. `LinesFromAss` 增加**舞台指示过滤**：源语言侧整段被 `*…*` / `[…]` / `【…】` / `（…）` 包住的行
   不配音（`*Gunshot*` 译文会丢星号，所以按 `{\rSrc}` 判断）。字幕保留，声音跳过。29 句 → 25 句。
3. **逐句 token 上限**：`kTokenHeadroom 1.6` × `PredictSeconds(kQwen3TtsPace)` × 12 Hz，
   下限 48（4 s）、上限仍是 900。此前固定 900 = 75 s，13 个字能生成 7.68 s、
   16 s 的 cue 直接顶到 72 s，事后只能 atempo 硬压——**变速正是「音色变了」的第二个来源**。

**验证**（长时平均谱相似度，对参考音）：
| 合成方式 | LTAS 相似度 |
|---|---|
| 不带参考音 ×3 | 0.817 / 0.899 / 0.825 |
| 带参考音 ×3 | **0.976 / 0.880 / 0.925** |

→ 克隆确实生效。whisper 抽查 v2 的 fit0/3/10/20：文本完整、无循环、无截断。

**仍未做**：**按角色**音色（需要说话人分离/嵌入，Python 的 `spk.py` + `step11_refs_auto.py` 那条链）。
现在全片一个嗓音，男女角色同声——这是「听起来不像原片」的剩余部分。

## 20. 按角色分音色 + 时间轴错位修正（2026-10-28）

**用户反馈**：「每一句都对不上，男女声音错配」。

**根因 A（时间轴，真的是 bug）**：`shift` 是**让步**（句子放不下才提前），但代码无条件
`shift = ShiftFor(room)`，于是前面只要有 ≥2 s 空白，句子就被提前整整 2 s——
字幕还没出来声音先到（实测 cue 60.00 → 58.00、117.00 → 115.04，每处长停顿都精确 −2.00）。
修正：`shift = min(ShiftFor(room), max(0, natural − window))`，放得下就不提前。
结果：中位偏差 0.60 s → **0.28 s**，长间隔句 +0.00~+0.56 s（密集段仍有合理让步）。

**根因 B（男女错配）**：全片只有一个参考音色，男女角色同声。
Python 的做法是「ECAPA 嵌入 + 人声分离 → 每角色 10–15 s 参考音」，C++ 两者都没有
（项目未引入 ONNX Runtime，也没有人声分离器）。按同样的**配置形状**用可得手段实现：
1. 抽取整片 16 kHz 单声道（一次 ffmpeg），逐句测 YIN 音高（40 ms 窗/20 ms 步，CMNDF，
   与 Python `_yin.py` 同算法）+ 浊音帧占比；
2. 以 **165 Hz** 分两组（男声 85–180、女声 165–255 的重叠中点），浊音占比 <0.2 的句子
   取最近邻句子的组；
3. 每组取「浊音占比 × 时长」最高的那句，剪 10 s 作该组参考音；
4. 逐句用本组参考 `--tts-speaker-file` 合成。
实测：低音参考 129 Hz / 高音参考 260 Hz，25 句分 4 低 + 21 高，逐句 F0 102–294 Hz 双峰分布。

**与 Python 仍有差距（明确记录）**：
| 项 | Python | 现在 |
|---|---|---|
| 说话人判定 | ECAPA 嵌入 + 分离后的人声 | 逐句音高 + 最近邻兜底 |
| 音色数 | 4（tom/celia/robot/elder） | 2（低/高） |
| 参考音来源 | 分离后 vocal stem，10–15 s | 混音里挑单句，≤10 s |
| 超窗处理 | 重写（≤2 轮） | 只 atempo + 掐尾 |
| 音效标注 | 有覆盖表 | 只过滤 `*…*`/`[…]`/`【…】`，无标记的（如「令人不安的音乐」）仍会念 |

## 21. 按角色音色：真接 ECAPA + 人声分离（2026-10-28，对齐 Python 全链路）

用户要求「完全参考 Python 的配置」。Python 的链路是：**人声分离 → ECAPA 说话人嵌入 →
0.55 余弦贪心聚类 → 每角色从 vocal stem 拼 10 s 参考音 → 逐句按角色克隆 → 伴奏垫底**。
本轮把这五步全部搬进播放器。

### 组件

| 文件 | 作用 |
|---|---|
| `src/SpeakerEmbedding.{h,cpp}` | ONNX Runtime **运行时动态加载**（`LoadLibrary` + `OrtGetApiBase`），ECAPA 图 192 维嵌入 |
| `external/onnxruntime/include/` | ORT C API 头（v1.31.1，4 个头文件；放在 external/ 以走 `/external:W0`） |

### 关键发现：0.55 这个阈值在本片是错的

把 Python 自己标好的 19 句（`F:/tmp/s2st/work/lines.json` 的 `speaker` 字段：robot/celia/tom）
当真值，在**整片** vocal stem 上跑阈值扫描：

| 阈值 | 声线数 | 纯度 | 合并了不同人(对) | 拆开了同一人(对) |
|---|---|---|---|---|
| 0.10 | 5 | 0.61 | 48 | 27 |
| **0.125** | **6** | **0.89** | **8** | **27** |
| 0.25 | 10 | 0.89 | 6 | 45 |
| 0.375 | 15 | 1.00 | 0 | 52 |
| 0.55 | 18 | 1.00 | 0 | 58 |

0.55 的「纯度 1.00」是假象——每句自成一簇当然不会混。**实测同人 0.18–0.39、异人 0.07–0.16**，
0.55 高于同人上限，等于不聚类。**改为 0.125**（`kClusterThreshold`），并加两级修正：
1. 簇中心相似 > `kClusterMergeThreshold`(0.15) 的合并（撤销过度切分）；
2. 句数 < 2 的声线并入**最近**的声线（不是「最多」的——两个主角时是抛硬币）。

### 排除的两条路（别再试）

- **CAM++**（`models/diar/speaker_campplus.onnx`，需 80 维 fbank）：同人 0.43 / **异人 0.67**，比 ECAPA 差。
- **sherpa-onnx 完整 diarization**（pyannote 分割 + CAM++）：同一段 180 s **分成 20 个说话人**。
- **音高**：本片男主自己的长句测出 **210–285 Hz**，与女主重叠；`_yin.py` 和 C++ 的 CMNDF 都一样。
  （这是 ECAPA 成为主判据、音高只做 fallback 的原因。）

### 参考音：拼接而不是单句

按 `step11_refs_auto.py` 的规则：同一声线取 1.2–6 s 的句子、**长的优先**、累加到 10 s
（上限 15 s），按**出场顺序**拼接，每段 5 ms 淡入淡出、段间 0.12 s 静音。总长 < 6 s 时
拒绝该声线（借用最近的）。实测 4 个声线剪出 12.2 s / 12.4 s / —（第 3 个句子太短借用）/ 10.5 s。

### 伴奏垫底（双轨导出也开）

分离有了 `no_vocals.wav`，于是 bed 从「整条原声（含英文）」换成**干净伴奏**，
并实现 Python 的闪避曲线：台词处 `kBackingGain`(0.85 × 单声道校正)、台词外 `kBackingRest`(1.0)、
150 ms 斜坡、台词前后各 0.2 s 预压。**不是**常压——常压会让片中真正的停顿听起来像断了音。

### 音效标注：补一条词表规则

`*…*`/`[…]` 标记能滤掉大部分，但译文常丢标记（`*Ominous music*` → 「令人不安的音乐」）。
加 `IsSoundDescription()`：整行 ≤10 字、以音乐/枪声/笑声…结尾、**不含人称与常用动词**才丢。
保守设计——漏掉一个音效词只多念一句；误删一句台词是观众丢失一句。25 句 → 24 句。
