# 跨管线经验吸收：Seed-VC 手册 → 本地 C++/ggml 配音方案

> 输入：macOS M1 Max 上跑通的 Seed-VC 管线手册（edge-tts 说法 → demucs 分离 → Seed-VC 克隆 → 排轴/归一化/混音/封装）。
> 问题：哪些能搬到本机（Win11 + 9070 XT）的播放器内置配音管线里，哪些不能。

---

## 一、结论先行

**能吸收的是方法论，不能吸收的是技术栈。** 三句话：

1. **Seed-VC / BigVGAN / demucs 这条 PyTorch 栈，不进播放器。** 本机实测无 `torch`、无 ROCm（`Program Files\AMD\ROCm` 不存在），要跑需装 ROCm SDK + `+rocm7.2.1` wheel（约 2.5 GB）。播放器是给终端用户的，不能要求终端用户装 ROCm —— 这是产品约束，不是技术优劣。
2. **但它证明了一件事：身份和语言要分开做。** 那边是 edge-tts 管"说什么/多快"，Seed-VC 管"谁在说"；本地是 Qwen3-TTS 一次采样同时决定两者，所以温度一动音色就飘。这条架构差异是"音色每句都变"的根因，本地能补的是把采样噪声压下去（已做：0.7 → 0.3）。
3. **四条可直接落地的工程经验**：参考音精选、中间产物缓存、上机自检、验收清单。前三条本地都缺，是下一轮的主要工作量。

## 四、下一步（按优先级）

**P0-1 ~~单句参考音~~ —— 已试，结论是反的（记录以免再试一次）**

用七句固定中文做对照（文本、温度、`-n` 全不变，只换参考音）：

| 参考音 | 七句的音高跨度 |
|---|---|
| 3 s，单句 | 49–64 Hz |
| 6 s，单句 | 126 Hz |
| 12 s，三句拼接 | 132 Hz |

看起来"越短越稳"，于是把参考音收到 3 s 单句跑了第 25 版 —— **整片 20 句里有 18 句跑到 255–343 Hz，男主角也被克隆成女声**。一句不够引擎抓，它就换成自己默认的说话人。

**教训：跨句子的音高跨度不是有效指标**，它主要是词句的韵律，不是音色。能把关的只有"落在哪"：男主角原音约 202 Hz，6 s 参考落在 117–209（中位 165），3 s 参考落在 280 —— 前者对，后者错。
已回滚到 6 s 两句（`DubFitPolicy.h`，`kReferenceTarget = 4.0` / `kReferenceCap = 6.0`）。

**P0-2 合成缓存（半天）**
`tools/dubbing` 里 77 句中间产物能带走是那边省时间的关键；本地每改一次参数就重合成 20 句（约 3.5 分钟）。
做法：缓存目录按哈希存 `fit*.wav`，命中则跳过合成，只重做混音。
验收：改混音参数后重跑，从 3.5 分钟降到 40 秒以内。

**P1 上机自检 + 一键验收（1 天）**
对应手册 §2 的"必须看到权重完全匹配"和 §6 清单。

**P2 批量合成（1-2 天）**
每句一次进程、每次重载模型（约 2 s）。20 句浪费约 40 s，整片 150 句浪费约 5 分钟。

## 五、假设与待核实（可一句话推翻）

1. **假设：终端用户不接受安装 ROCm + PyTorch。** 如果这条配音能力只给自己出片用、不当作播放器功能，Seed-VC 那条路可以重开（需先装 ROCm 7.2.1 + torch rocm wheel，本人未实测，工期 1-2 天且不确定）。
2. **假设：单句参考优于多句拼接**，依据只有一组对照（女声单句 vs 男声拼接），样本量 2，需 P0-1 验证。
3. **待核实**：Qwen3-TTS 是否存在"身份锁定"参数（如 speaker embedding 直传、或更低的温度下限）。若存在，比调参考音更省事。
4. **待核实**：llama-tts 是否支持一次加载合成多句。若支持，P2 的收益从 40 s/片 提高到 5 分钟/片。

## 6.2 元教训（P0）：选验收指标前先问"它能否区分成功与失败"

四次同型踩坑 —— 三个本地、一个来自这份手册。**模式完全一样：指标会返回数字，但那个数字与成败无关。**

| 指标 | 看起来像 | 真相 | 该看什么 |
|---|---|---|---|
| `torch.cuda.is_available()`（手册 §5.1） | GPU 可用 | AMD 上也返回 True，只说明兼容层在 | `get_device_name()` 是否显示你的卡 |
| 每句 F0 跨度（本文 P0-1） | 越短音色越稳 | 主要是词句韵律；照它调参，整片 18/20 句变女声 | "落在哪"（男主原音 ~202 Hz） |
| 峰值 dB（验收母版） | 判断是否削波 | 编码器过冲不可控，合格片也可能越界 | 解码后**过零样点数**（源片自身 249 个） |
| 短片 ECAPA cos（派角） | 能分开两个人 | 只有"句子本身在参考音里"才 0.6+，其余 ±0.15 是噪声 | 呼语锚点 + 成品参考音重判 |

**规则**：指标上机前先跑一组"已知好 / 已知坏"对照；分不开就换指标，宁可不判也不假判
（`docs/SUBTITLE-AUDIO-METRICS-zh.md` §2.4 的"宁可少判，不可错判"是同一条）。
**"能跑出数"不等于"能判断"** —— 这条比任何具体参数都更容易让人白干一轮。

## 6.4 实测：llama-tts 每句进程开销 —— 已证伪清单（别再试）

整片 106 句配音约 8.8 分钟，其中**每句一次 `llama-tts.exe` 进程**是最大头。
实测（每句都验了产物，不只看时间）：

| 试过的 | 单句耗时 | 判定 |
|---|---|---|
| 冷启动（基线） | 5.3 s（生成仅 1.64 s） | **初始化 ≈ 3.65 s**，生成只占 1/3 |
| 热启动（页缓存已命中） | 4.8 s | 只快 0.4 s → **页缓存无效** |
| 去掉 `--tts-speaker-file` | 4.88 s | 不是参考音的开销 |
| 限线程 `-t 8` | 4.62 s | 线程数无关 |
| 并行 3×2（各 `-t 6`） | 3.5 s/句 vs 串行 4.0 s/句 | **只快 12%**，不值得引入并发 |
| 并行 4（不限线程） | 29.7 s/4 句 vs 串行 16.3 s/4 句 | **比串行还慢一倍**（24 核被 4×24 线程超订） |
| GPU `-ngl 99` | 总 4 s（生成 1.13 s） | 生成快了，收益被初始化吃掉 |

**结论：固定初始化 ~3.2 s/句，参数、并发、缓存、GPU 都消不掉。** 唯一真解是
"一次加载、批量合成"，而工具侧不支持：

- `llama-tts.exe` 是纯一次性 CLI（`-m -mm -f -o`），**无 server 模式、无批量模式**
  （`-rpc` 是分布式后端，不是 TTS 服务）。
- `llama-server.exe` 0.3.0-dev（build 10679）**不支持 TTS** —— 无 `--tts-*` / `/v1/audio/speech`。
  常驻服务方案要换支持 TTS 的新版二进制，或改 llama.cpp 的 tts example 重编译。

三条落地路径（成本从低到高）：**合成缓存**（半天，不改首次、只让重跑从 8.8 分钟降到几十秒）→
**换支持 TTS 的 llama-server**（依赖外部二进制）→ **改 llama.cpp 重编译**（1-2 天）。
**本轮决定：放弃** —— 8.8 分钟对整片一次成片可接受，优先级低于音色与字幕质量。

### 过程教训（实例）

前两轮测量**只记了时间、没验产物**：配音收尾会清理 `lineN.txt` 与 `voice-1.wav`，
那批命令全部瞬间失败，读数是"并行 0 秒 / 串行 1 秒"的假信号，差点当成结论。
**"命令退出 ≠ 命令成功"** —— 测吞吐必须先验产物存在，这正是 6.2 那条规则的反面例子。
