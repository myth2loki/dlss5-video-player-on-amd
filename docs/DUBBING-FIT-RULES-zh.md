# 配音逐句拟合：参数与教训（Convert Video 第二期实现依据）

_最后更新 2026-10-27。每个数字都是本机实测（RX 9070 XT / Ryzen，Tears of Steel 734 s / 71 句），不是估计。_

这份文档不是管线设计（那是 `deliverables/dubbing-pipeline-方案.md`），是**实现时必须照做的规则**：
一条译文怎么塞进它那几秒窗口、声线怎么判、放不下时按什么顺序让步。
它存在的理由很直接——这些规则是在 `F:/tmp/s2st` 的脚本里试出来的，
而那个目录不是 git 仓库，一次清理就没了；照方案文档里实验前的参数实现，会把这些坑原样重踩一遍。

两个模块已经进了仓库（`tools/dubbing/glossary.py`、`tools/dubbing/subtitles.py`，与
`F:/tmp/s2st` 里的运行副本逐字节相同）：它们分别是「术语表」和「字幕同源」的实现，
也是这份文档里最容易实现错的两条。其余 31 个脚本仍在 `F:/tmp/s2st`，尚未入库。

**心法：自然时长必须服从窗口，但让步的顺序决定了听众听到什么。**
顺序是「借静音 → 加速 → 重写 → 掐尾」，每一档都有上限，超了就报出来，不许静默丢字。

## 1. 窗口怎么算（这是最长的一条教训）

```python
window = next_start - start            # 不是 end - start
window = min(window, base + 1.5)       # 不许吃到很远之后的空隙
window = max(0.5, window)              # 下限，见 §2 的重叠
```

- **`next_start - start`，不是 `end - start`。** 一句话在 389.71 s 说完，它仍然占着静音到 390.50 s，
  那 0.41 s 的静音正是让一句需要 1.0 s 的中文能装进一句 0.41 s 英文的地方。
  用 `end - start` 会让几乎每一句都"超窗"，然后疯狂加速。
- **跳过不说话的行。** 后面的行如果被删（译文为空、或覆盖表给 null），窗口要一直延伸到**下一句真的要说的话**。
  否则删掉一句的结果是它的邻居对着空气干等，而窗口却按那个不存在的边界算。
- **上限 `base + 1.5 s`**：没有这个帽子，片中一个长停顿会把某句的窗口撑到十几秒，那句就不叫"拟合"了。

## 2. 让步顺序（照这个顺序，别调换）

| 档 | 动作 | 上限 | 代价 |
|---|---|---|---|
| 0 | 合成后**裁首尾静音** | −48 dBFS，两端各留 40 ms | 无（见 §3） |
| 1 | **借前一句留下的静音**（起点前移 `shift`） | `MAX_SHIFT = 2.0 s`，且要留 0.15 s 不撞上一句 | 无，听觉上完全不可辨 |
| 2 | **atempo 加速** | `MAX_TEMPO = 1.25`；短窗（<1.2 s）`MAX_TEMPO_SHORT = 1.50` | 轻微；>1.55 人耳判"急" |
| 3 | **让翻译引擎按字数预算重写** | 最多 2 轮（`MAX_ROUNDS`） | 会丢意思（见 §3 第 3 条） |
| 4 | 放弃，**报出来** | — | 留给混音阶段掐尾，并进日志清单 |

两处上限容易被写错：

- **`REWRITE_ABOVE` 故意等于 `MAX_TEMPO`（1.25）**：凡是加速能吸收的溢出，就不要去问翻译引擎——
  问它才是把句子写坏的那一步。
- **短窗阈值 1.2 s 和 1.50× 是一套的。** 短窗里是感叹句（"No!"、"Whoa!"），引擎自身的时长方差比窗口还大
  （节奏模型承诺「不！」0.54 s，实际合成 0.96 s）。人遇到感叹句本来也会念快，半秒足够；
  只调倍数不调阈值，普通从句会被判成感叹句。

**先算再合成**（2026-10-27 补）：在调引擎之前，先用节奏模型算「这句最多能拿到多少秒」——
窗口 + 可借的静音（同 §2 档 1 的口径）+ tempo 上限，得到一个 `reachable`。预测超了就直接进档 3
重写，不必先合成一遍再量。

```python
reachable = (window + min(room, MAX_SHIFT)) * ceiling
if predict(text) > reachable + pace["mae"]:
    → 先重写，再合成
```

**只往"没救"的方向用这个预测**：节奏模型的 MAE 是 0.236 s，"3.0 s 塞进 0.50 s 窗口"是事实，
"1.1 s 塞进 1.0 s 窗口"是猜测。本片拦下 2 句（#2、#7），省掉两次必废的合成；
#17（0.50 s 窗口想放「你是一位明星」）也是这么被提前判死的。

## 3. 三个反直觉的点

1. **先借静音，再加速。** 这两个顺序反过也可以"跑通"，但把句子往前挪进前一位说话人留下的空隙，
   听众完全听不出来；同样的时间靠 atempo 挣，就听得出来。代码注释里写反过一版，实际行为也跟着反了。
2. **裁静音不是美化，是预算。** 「哇！」曾经合成出 1.68 s（一个字），拟合阶段于是花了整个窗口去加速一段静音，
   混音阶段只好把这句话截短。裁掉两端死气之后，同样的句子直接装进窗口。
3. **重写一定会吃掉意思。** 让翻译引擎"用 8 个字重说这句"，它会删掉看起来次要的从句：
   `All right, fine. I'm freaked out.` 被压成「没事，没关系。」——"我有点害怕了"整句没了，只为了省 1 s。
   反向也有：`Get her coming, we have two minutes left.` 上一轮被压成「快叫她来，只剩两分钟。」，
   这一轮用回完整译法反而更准。**所以重写必须是最后一档，且要人耳抽查。**

## 4. 覆盖表（`zh_overrides.json`）

```json
{ "3": "你有你的机器人，我只想在太空闪耀。", "25": "走走走！", "60": null }
```

- 键是行的 `index`（不是数组下标），值是**要替换的译文**；值是 `null` 表示**这一句整句不配**。
- 三种非它不可的场合：
  - **两句共用一段语音**：转写器把 `You forgot me on Earth!` 和 `I know.` 标在同一段（377.3 s）。
    两句都配，就会为了给后一句腾地方把前一句截成两半——所以后一句置 `null`，保留原声。
  - **短感叹句塞不进去**：`Go, go, go.` 直译「出发，出发，出发。」ratio 2.27，永不进窗；
    换成「走走走！」ratio 1.00。中文口语本来的说法，比强行加速靠谱。
  - **专名/习语**：`And a dick.` 直译「以及一个。」——改成「而且还是个混蛋。」
- 覆盖表要能**活过重跑**（`--from fit` 不覆盖它），否则每次调参都要重打一遍。
- 除此之外还有一张 `GLOSSARY` 做机械替换（`凯莉/西莉亚 → 塞莉亚`）：同一个名字在不同翻译轮次里会被译成不同写法。

## 5. 声线：只允许否决，不允许指认

`step1` 用 ECAPA 嵌入 + 余弦对每个声线中心做归属，要求 0.15 的余量。**70 句里有 29 句达不到这个余量**，
全是 0.4~1.0 s 的短感叹（"Now."、"Be honest."、"Be tender."）：ECAPA 在这种长度上绝对余弦掉到 **0.03~0.17**，
胜者由噪声决定。其中 4 句被判成女主，而画面里是男人在跟机器人说话——成品里听得出来。

补救用的是**基频否决**（parselmouth/Praat 自相关 `to_pitch_ac`，双频带覆盖率）：

| 声源 | 165–350 Hz 有声覆盖率 |
|---|---|
| tom（男，有真值的行） | 0.14 – 0.31 |
| celia（女，有真值的行） | 0.63 – 0.88 |
| 出问题的那段（232–248 s） | 0.00 – 0.37 |

- **单边否决**：`hi_coverage < 0.40` ⇒ 这个声音不可能是女主 ⇒ 只能是男声。
  反过来不成立（两个男声频带重叠），所以它**永远不会"指认"**某个声音是谁，只能否决。
- **按"场"判，不按句判**：同一场对话里声线连续（`TURN_GAP = 6.0 s` 之内算同一场），
  一句长度不够不足以判，一场就够。
- **`unknown` 标签绝不能"借给句数最多的声线"。** 兜底策略曾这么干，而句数最多的是 celia，
  于是 15 句短感叹全变女声——这就是"4:00 男人说话却是女声"的根因。宁可留 `unknown` 用中性处理。

## 6. 混音（`step13`）的三件套

1. **两句话撞在一起是唯一不可接受的缺陷**（背景音乐里藏不住，听众立刻察觉）。
   处理顺序固定：先加速（上限 `HARD_TEMPO = 1.35`，比拟合阶段的 1.25 高一档，因为此时没有别的选择），
   还不行才**掐尾**，并且掐尾的句子要进清单打印出来。行间至少留 `MIN_GAP = 0.03 s`。
2. **没配上中文的行必须补回原声**，否则画面上嘴在动、声音是空的（人声轨已经被整条挖掉）。
   **只能逐行补**：拿人声轨扫"未被覆盖的语音段"会把每句的尾巴都当漏配，
   实测这样往一条 12 分钟中文轨里灌了 60 s 英文。
3. **bed 只在该响的地方压**：基线 `GAIN_BACKING = 0.85`（相对等响的 mono 和），
   有中文行的地方再压 **−3 dB**，边缘 **150 ms 斜坡**（否则每次闪避都"咔"一声）；
   逐句语音电平（20 ms 块 75 分位）对齐到全片中位数，钳在 ±12 dB；出口过 4× 过采样 limiter
   （`limit=0.794` = −2 dBTP，`latency=true`），母版落 −1.9 dBTP 再编码。
   **不要用整段 RMS 归一**：句尾静音会让"很轻"的长句被推高，实测偏 3~4.9 dB。

|---|---|---|
| 超窗句数 | 6（最高 ratio 2.27） | **0** |
| 被掐尾 | 7 | **3**（#17 / #54 / #55） |

## 8. 别照抄的旧结论

`deliverables/dubbing-pipeline-方案.md` §13.3 与 `tts-engine-recommendation.md` §11 是实验早/中期的快照，
和实测冲突的地方以本文为准：

| 旧文档说 | 实测 |
|---|---|
| 溢出只用外部 atempo，**上限 1.20** | 1.25；短窗 1.50（§2） |
| 合成 `do_sample=False`、固定种子 | 实际用的 llama-tts 是 `--temp 0.7` 采样：**同一句两次时长不同，超窗集合每轮都会变**。所以不能拿一轮的清单当结论 |
| 引擎定案 XTTS-v2 | 产出 `tears_of_steel_zh_20mb_v2/v3.mp4` 的是 **llama-tts + Qwen3-TTS-12Hz-1.7B-Base Q4_K_M**（+ `mmproj-…Q8_0`）。XTTS 只在 `ab_refs/xtts_*.wav` 留下过试听片段 |
| 模型只用 atempo 就够 | 还需要 §1 的窗口定义、§2 的顺序、§4 的覆盖表 |

因为 TTS 是随机采样，**同一份译文重跑两次，超窗的句子不是同一批**。
调参时不要用"上次那 6 句"当固定靶子，要跑两三轮看集合是否收敛。

## 9. 字幕：从配音的行里长出来，不要另取一份

**规则：字幕的文本和时间都必须来自 `fit_auto.json`（配音实际念的那一行），不能来自
`zh_final.json`（翻译草稿）。**

曾经两条链各取一个文件：字幕读 `zh_final.json`，配音读 `fit_auto.json.text`。覆盖表
（§4）和 budget 重写只改了后者，于是 71 句里有 **13 句**屏幕上和耳朵里不是同一句话
（`天啊！` / `我靠！`，`她为什么这样做？` / `为啥？`）。更根本的是**成品里根本没有字幕轨**，
所以这个错谁也发现不了。

修法（`tools/dubbing/subtitles.py`）：

| 字段 | 取自 | 为什么 |
|---|---|---|
| 文本 | `fit_auto.json.text` | 引擎念的就是这一串，改一个字要重合成 |
| 起点 | `anchor` | fit 可能把句首前移借静音（§2），字幕要跟着走 |
| 终点 | `anchor + seconds` | `seconds` 已含 tempo 压缩，是真正说完的时刻 |

三条生成期约束（写进生成器，不是事后检查）：

1. 停留 ≥ **0.8 s**，但**下一位说话人抢先开口时让位**——重叠不可接受，短缺可以接受
2. 单行 ≤ **32 单位**（CJK 记 2），超了按标点断行；标点离均分点太远就硬切
3. 起点与配音起点**必须完全相同**，不要用源 cue 的 `start`（那会差 0~0.5 s）

容器细节：mp4/mov 用 `mov_text`（丢样式、保文本与时间），mkv 用 `ass`（样式保留）。
语言标签写 **`chi`**，写 `zho` 会被 mov 容器静默丢弃——那时播放器不会默认选它。

效果（本片实测）：阅读速度 max 26.3 → **7.7 字/秒**，超宽行 7 → **0**，
字幕与配音不一致 13 → **0**。

## 10. 与播放器的接线现状（2026-11-11）

2026-10-27 这一节写的是「以上只在 `F:/tmp/s2st` 的 Python 链里成立，播放器只做画面」。
2026-10-30 那条作废，下面是真的接法，本节不再描述计划。

**对话框**：Convert video 的 *Sound and text* 组第三行是 `Dub it into that language`
（键 `convert.dub`，选项 `Do not dub` / `Chinese`）。勾它会把 *Translate the speech* 一并打开、
*Subtitles* 至少设成软轨——没有译文就没有可念的句子。缺语音引擎时这一行灰掉，
提示里点名缺哪个文件（`convert.tip.dub.no_runtime` / `no_runner` / `no_model` / `no_mmproj`）。

**顺序**：文字阶段（转写 + 翻译）→ 配音阶段（`dub::RunDub`）→ 画面阶段 → 封装。
配音从文字阶段写出的 ASS 里读行（`dub::LinesFromAss`），所以字幕与配音天然同源；
封装把它当第二条音轨写进去（`-map <dub>:a:0`、`aac 256k`、`language=chi`、
`-disposition` 把它设成唯一的默认音轨），原声轨保留、不设默认，切回来只要一个菜单。
「同源」在 2026-11-11 之前只是名义上的：字幕一条 ASR 段、配音一句合并过的句子，
两边的时间轴对不上。现在合并发生在文字阶段，见 §11。

**"第二期"那条要求被遵守了**：没有新造"没有帧数的阶段"。配音的份额按行登记到已有的
进度条上（`StageExportUpdate::overallCompleted/overallTotal`），面板不会消失一次。

| 用途 | 文件 | 缺了会怎样 |
|---|---|---|
| 语音 | `dub/runtime/llama-tts.exe`（每行一个进程，约 3.2 s 启动） | 拒绝，行灰掉 |
| 语音模型 | `dub/models/*.gguf` + `mmproj-*.gguf` | 拒绝，说缺哪个 |
| 说话人 | `dub/models/ecapa_voxceleb.onnx` + `dub/runtime/onnxruntime.dll` | 降级到音高判性别 |
| 伴奏分离 | `dub/stems/stems-split.exe` + `dub/stems/models/*.gguf` | 不分离：说话人特征在混音上测、**配音之下不垫伴奏**（日志写明） |

**常量在哪**：本文所有数字都在 `src/DubFitPolicy.h`，`PolicyTests` 有八条用例把它们钉住
（窗口口径、让步顺序、允许减速、聚类标定、语速模型、重写预算、填满预算、填满的校验）。
改常量会红，改注释不会。

## 11. 文本阶段：一句话一条字幕（2026-11-11 实测）

用皇家学会那段 3 分钟访谈（1080p25、双人同框、无字幕条、分离后伴奏只有 −65 dBFS）跑产品链，
量出三件事；三件都在文本阶段修，不在配音阶段补。

**① ASR 的断句就是字幕的断句，这是错的。** whisper 在每个停顿处切句，文字阶段一句一 cue：

| | 修前 | 修后 |
|---|---|---|
| cue 数（180 s 素材） | 109 | 24 |
| 时长中位 | 1.43 s | 5.93 s |
| 源文字数中位 | 8 | 94 |
| ≤4 字 | 34 条 | 0 |
| <1 s | 39 条 | 1 |

「从现在开始」「温度」「3摄氏度」本来是同一句，被拆成三条各自翻译、各自上屏。
更糟的是**配音阶段自己合并了**（`Dubbing.cpp` 的 `MergeSentences`），字幕没有——声音连成句、
字幕一蹦一蹦，观众听出来的就是两者不同步。

现在合并发生在 `ReadCues` 之后、翻译之前（`subtitle_translate::MergeIntoSentences`），
字幕和配音读的是同一批 cue，配音那侧的合并退化成空操作。规则：上一句没以句末标点结束
（这一条是硬条件，句末标点一律不接）、间隔 ≤ **0.6 s**、合并后跨度 ≤ **16 s** 就并；
再给短于 **1.2 s** 的行补足停留（但不越过下一条的起点）。

间隔取 0.6 是量出来的，两头都试过：

| 间隔 | cue 数 | 时长中位 | 症状 |
|---|---|---|---|
| 0.35（配音那侧的值） | 34 | 3.0 s | 「When」/「did you first discover…」间隔 0.43 s 被切开 |
| 0.45 | 30 | 4.2 s | 「climate」/「change.」间隔 0.48 s 未并，屏幕上只剩「气候」，三秒后才「改变。」 |
| **0.6** | **24** | **5.9 s** | 上述两处都并上 |
| 0.8 | 24 | 6.1 s | 不再多并任何一条，只是把停顿吃得更狠 |

代价是长句：P90 是 15 s，最长 15.7 s，双字幕在屏幕上能占三到四行。**这一条已经补上了**——
「一条配音、两条字幕」，见下面 ④。

**② 名字是知识，不是语言。** `University of Reading` 译成「阅读大学」，`Dartmoor` 译成
「达特茅斯」。合并句子救不了这一类：句子完整，模型只是不知道这个地名。

试过让模型自己产术语表，**结论是不用**：

| 问法 | 答案 |
|---|---|
| 「给出通行译名」 | `University of Reading=牛津大学`（另一所大学）、`Dartmoor=达特茅斯` |
| 「按音译」 | `阅读大学`（译义）、`达特穆尔` ✓；但它对熟悉的名字会答成拼音（`伦敦=lún dūn`）或繁体 |
| 两次取交集 | 人名一致（`汉娜·克洛克` 两种问法相同），地名全部不一致 → 只剩人名 |

术语表改成**用户提供的文件**：`film.mkv` → `film.names.txt`，一行一个 `英文=中文`
（`=` 或 `:` 均可，`#` 开头是注释）。命中的行在 prompt 的**指令里**说明译名，不塞进正文
（塞进正文会被当成待译内容）。实测 `雷丁大学` / `达特穆尔` / `汉娜·克洛克` 三条全部落实。
文件缺失时行为与以前完全一致。解析和注入是 `ParseGlossaryFile` / `RenderingsFor`，有用例。

**③ 放不下的行，回头问翻译要短的。** 中文译文天然比英文长。这段 180 s 的素材上：

| 配置 | 行数 | 要压语速 | 连最快速率也放不下、被混音截断 |
|---|---|---|---|
| 修前 | 34 | 25 | 0 |
| 只合并句子（①） | 30 | 23 | 3 |
| 合并 + 重问（①③） | 24 | 20 | 1 |

合并把碎片并成整句之后，单句更长、窗口不变，于是「怎么念都放不下」的行从 0 变成 3——
这也是为什么 ③ 必须跟着 ① 一起做。

配音那侧的让步顺序（借静音 → 变速 → 重写）里，「重写」一直没接上——`Dubbing.h` 的注释
原本写着「reported and cut by the mix」。现在在文本阶段就判：`dub_fit::BudgetForLine`
用同一套语速模型（7.02 字/秒、每个逗号 0.665 s）预测这行要念多久，跟 `WindowSeconds` +
`ReachableSeconds` 比；**只用 `IsHopelessBeforeSynthesis` 判死刑**（模型误差 0.236 s，
"3.0 s 放不进 0.5 s" 是事实，"1.1 s 放不进 1.0 s" 只是猜测），判了才按字符预算重问一次，
答案更短才采用。预算按**逗号密度**折算，不能按原句逗号个数扣——否则会问出
「6 个字里还要三个逗号」这种自相矛盾的预算。预算低于 8 字（`kMinRewriteCharacters`）就不问：
那种行怎么改都放不下，交给混音，和以前一样。

这段实测 2 句被重问，其中 105 → 49 字那一条顺带把两个没译的英文节目名译成了
《野性天气：我们的世界面临威胁》《生命科学》。

**④ 长句切成两三条显示行，配音仍读整句。** 合并之后最长的一条 15.7 s / 75 字，1080p 上
是一整段文字。切法（`SplitForDisplay` / `CutOneForDisplay`）：每条 cue 按
`max(时长 / 6.5 s, 字数 / 48)` 算需要几个屏，封顶 3 个；切点只落在**逗号、顿号、分号、冒号之后**
（句号不切，理由见下），并尽量等分。

契约是「**只切给眼睛，不切给耳朵**」：切出来的几条首尾相接（gap = 0）、前几条都不以句末标点
结尾、原文按同一比例在空格处切开，于是配音侧 `MergeIntoSentences` 会把它们并回同一句。
实测 24 句 → 39 条显示 cue，配音阶段仍是 **24 spoken / 20 tempo / 1 cut**，与切分前逐项相同：
语音一个字都没变，变的只有屏幕上怎么排。

| | ③ 之后 | ④ 切分 |
|---|---|---|
| 显示条数 | 24 | 39 |
| 时长中位 | 5.93 s | 4.44 s |
| 最长 | 15.68 s | 9.24 s |
| 字数中位 | 29 | 23 |
| 最长字数 | 82 | 41 |

顺带修掉一个更严重的问题：**中文在 libass 里根本不换行**。`WrapStyle 0` 只在空格处断行，
中文没有空格，超过一行的句子直接被画到画面外，左右两端各裁掉一截——英文有空格、能正常折断，
所以只有中文露这个 bug，而合并句子（①）之后句子变长才看得见。现在 `WrapRows` 按
「可用宽度 / 字号」手动插 `\N`，优先断在标点之后，且断点不会让下一行以 `，`／`。` 开头。
实测 40 个汉字在 1920 上排出来 1878 px（≈0.76 em/字），而这里按 1 em 折算——宁可早断一行，
也不能裁字。

`DubTextOf` 同时改了一处：`\N` 夹在两个汉字之间时不再变成空格，否则配音会把换行读成停顿。

**要不要在整片链（`termfull`）上重跑**：① 是结构性的，值得；② 术语表按片提供；③ 属于调优，
配音不是这条链的交付物，可以不动；④ 只影响上屏，不重跑也能单独套到已有 ASS 上（它就是
`BuildAss` 里的排版，配音读回来的东西不变）。

**还没做的**：整片端到端只能手动跑（`DubConvertE2E.exe`，要三套引擎、几分钟，故意不进 ctest）；
角色识别在配乐混入的 stem 上仍有 20~30% 的句子判错性别，这是当前上限，不是调参问题。

## 12. 分男女：判定口径共用，但 speaker 参考音有个陷阱（2026-11-12）

独立工具 `F:/dlss5-video/yt-tools/YouTubeSubtitleCN` 先把「分男女」做出来了，判定口径
**照抄播放器**，两边对同一句不会给出不同答案（`src/gender.py` 是可直接移植的参考实现）：
YIN 累积均值归一化差分（40 ms 窗 / 20 ms 跳 / 最多 8 s / 第一个低于 0.35 的谷）、
浊音帧基频中位、`kVoiceSplitHz=165`、`kVoiceMinVoiced=0.20`；
148~168 Hz 缓冲带与帧投票纯度 <0.70 判「无意见」，再继承最近一句的性别。

⚠️ **播放器当前可能没有真的分男女**：`Dubbing.cpp` 的 `lineReference[index]` 是从视频
切出来的**原声片段**，直接传给 Qwen3-TTS 的 `--tts-speaker-file`。实测这条路径：

| 参考音（源） | 参考音 F0 | 克隆出的中文 F0 | 结果 |
|---|---|---|---|
| 电影英语男声 | 113.5 Hz | 186.0 Hz | 女声 |
| 电影中文配音男声 | 115.9 Hz | 235.3 Hz | 女声 |
| 访谈英语女声 | 177.8 Hz | 192.8 Hz | 女声 |
| 无参考音 | — | 235.3 Hz | 女声 |

外部音频与模型的 speaker 编码分布不匹配，被映射进它自己的女声区 → 男声角色仍由女声念。
**别用 FFT 自相关 argmax 代替 YIN**：实测电影音轨上大量句子被读成正好 400 Hz（算法上限），
是错八度；换成 `PitchOfFrame` 那套累积均值归一化差分后误报消失。

正解是**用引擎自己生成的 wav 当锚**：不带 speaker 随机采样时它本来就会吐出男声
（93/103/106/117 Hz）和女声（186/201/202/241 Hz），挑一男一女存成两条内置声线，
再让每句克隆对应性别的锚。12/12 次跨文本性别稳定：男锚输出 89~142 Hz，
女锚输出 185~258 Hz。独立工具已把两个锚放在 `bin/tts/voices/`，并在日志里回显
「判定 男N/女M」与「实测 男N'/女M'」，避免「下游静默拒绝、上游不回显」。

代价要讲清：这样**音色不贴原片本音**，只是两条固定中文声线。用户的验收口径是
「尽量贴本音，并不要求完全一样」：要贴本音得走 Seed-VC **逐句自参考**那条链
（cos 0.50），而不是它的 `f0_condition`——后者 11-11 已实测 15 条对照，
cos 0.545 → 0.528、慢一倍，反而更差。Qwen3-TTS 本身没有音高控制入口，
这条路只负责分男女。播放器侧要修的话，改动点是 `lineReference` 的来源
（换成内置锚 + 按 `CuePitch` 选路），不是判定阈值。

## 13. 填满窗口：句子说不满的那一半（2026-11-12）

上面 §1–§3 全部在讲「太长怎么办」。反过来的一半更常被听见，而这一轮才发现播放器
一直没做：**中文比它占的那个窗口短**，话说完、画面还在说，剩下的是纯伴奏。观众描述的
不是「翻译短」，而是「两句之间断了」。

独立工具上先量到了，再修：

| 位置 | 现象 | 成因 |
|---|---|---|
| 2:41–2:57 | 尾部空 **4.37 s** | 64 字 / 窗口 15.8 s，判「够长」跳过扩写 |
| 3:45 | 尾部空 **8.23 s** | 字幕 17 字，按 1.8 倍算上限只有 30 字 < 需要的 57 字 |
| 全片 | 句尾静音合计 **≈68 s** | 48 句里 31 句说不满 |

**规则**（`src/DubFitPolicy.h`，`FillForLine` / `FillIsSafe`）：

1. `kFillTarget = 0.92`：目标不是 100%，因为语速模型的误差是 0.236 s，瞄着满窗的行
   最后一定会被排轴压一下。
2. `kFillMinSeconds = 0.35`：差得比模型误差还少就不值得再合成一次。
3. `kFillInfoFloor = 0.55`：**低于窗口 55% 不是「翻译短」，是「另一句话」**——4 秒的
   英文旁白译成 4 个汉字，让模型扩到四倍，它只会编。这类行保持原样，静音留着。
4. `kFillCapRatio = 1.10`：候选超过预算 10% 不用，排轴的 atempo 只能吃掉 3%。
5. `FillIsSafe`：必须变长、不得超预算、**数字集合不得新增**。第 5 条是最容易漏的：
   提示词写「不得新增事实」不管用，4B 模型照样造出「一共 5 次」；独立工具上还出现过
   `[说话人姓名]` 占位符和 17 字变 108 字。数字是唯一能被机器判死的「新事实」。

**窗口用 `end - start`，不用 `WindowSeconds`。** 后者会借句后最多 1.5 s 静音，用它当
放慢目标会把话拖进下一句的地盘，K 帧上就是嘴停了声音还在走。原演员停在哪，中文就停在哪。

**为什么不是「放慢一点」就够了**：`kMinTempo = 0.85`，最多给回 15%；而说不满的行通常
差 30–40%。放慢只在补完字之后兜剩下的零头。所以在 `Dubbing.cpp` 里顺序是
**先扩写（合成前）→ 再加速/放慢（合成后）**，扩写拿的是 `FillForLine` 的预测，不是
合成后的实测——扩写必须在合成前，否则要多跑一次 TTS。

**扩写不碰字幕。** 文字阶段已经把 ASS 写盘了，配音阶段改的是 `spokenText` 这个局部量，
所以「听到的」变长、「看到的」不变。这和独立工具的 `Cue.dub_text` 是同一个决定：
`dub_text` 只给配音，`translation` 仍是字幕。

**两套语速模型不能互换。** 独立工具用 edge-tts，实测 5.6 字/秒（878 字 / 156 s）；
播放器用 Qwen3-TTS，标定是 7.02 字/秒 + 每个逗号 0.665 s。所以 `kFillTarget`
这类**比例**可以照搬，`characters` 这个**绝对字数必须由各自模型算**
（`CharactersForSeconds`），直接搬 5.6 会把预算放大 25%。

**判据**：`Dub:` 汇总行多了 `N re-worded longer`；单行日志是
`would speak X s of a Y s line; filling it to Z characters`。全片 `filled` 为 0 而
`compressed` 很高，说明阈值或密度折算写错了，先看这两行再怀疑模型。

**实测**（独立工具，同一条 240 s 访谈，全链 dist 版）：

| 指标 | 修前 | 修后 |
|---|---|---|
| 配音总长占比 | 198 s / 82.5% | **224.8 s / 93.6%** |
| 全片句尾静音 | ≈68 s | **≈17 s** |
| 最大单处接缝 | 4.37 s | **0.31 s** |
| 漏出英文 | 0/223 | **0/223** |

播放器侧这一版只加了扩写与校验，**没有**跑整片端到端（`DubConvertE2E.exe` 要三套引擎）；
`PolicyTests` 的两条用例钉住的是阈值与校验，不是听感。
