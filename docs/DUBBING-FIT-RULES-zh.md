# 配音逐句拟合：参数与教训（Convert Video 第二期实现依据）

_最后更新 2026-10-27。每个数字都是本机实测（RX 9070 XT / Ryzen，Tears of Steel 734 s / 71 句），不是估计。_

这份文档不是管线设计（那是 `deliverables/dubbing-pipeline-方案.md`），是**实现时必须照做的规则**：
一条译文怎么塞进它那几秒窗口、声线怎么判、放不下时按什么顺序让步。
它存在的理由很直接——这些规则是在 `F:/tmp/s2st` 的脚本里试出来的，
而那个目录不是 git 仓库，一次清理就没了；照方案文档里实验前的参数实现，会把这些坑原样重踩一遍。

**心法：自然时长必须服从窗口，但让步的顺序决定了听众听到什么。**
顺序是「借静音 → 加速 → 重写 → 掐尾」，每一档都有上限，超了就报出来，不许静默丢字。

---

## 1. 窗口怎么算（这是最长的一条教训）

```python
window = next_start - start            # 不是 end - start
window = min(window, base + 1.5)       # 不许吃到很远之后的空隙
window = max(0.5, window)              # 下限，见 §2 的重叠
```

- **`next_start - start`，不是 `end - start`。** 一句话在 389.71 s 说完，它仍然占着静音到 390.50 s，
  那 0.41 s 的静音正是让一句需要 1.0 s 的中文能装进一句 0.41 s 英文的地方。
  用 `end - start` 会让几乎每一句都"超窗"，然后疯狂加速。
- **跳过不说话的行。** 后面的行如果被删（译文为空、或覆盖表给 null），窗口要一直延伸到**下一句真的要说的话**。
  否则删掉一句的结果是它的邻居对着空气干等，而窗口却按那个不存在的边界算。
- **上限 `base + 1.5 s`**：没有这个帽子，片中一个长停顿会把某句的窗口撑到十几秒，那句就不叫"拟合"了。

## 2. 让步顺序（照这个顺序，别调换）

| 档 | 动作 | 上限 | 代价 |
|---|---|---|---|
| 0 | 合成后**裁首尾静音** | −48 dBFS，两端各留 40 ms | 无（见 §3） |
| 1 | **借前一句留下的静音**（起点前移 `shift`） | `MAX_SHIFT = 2.0 s`，且要留 0.15 s 不撞上一句 | 无，听觉上完全不可辨 |
| 2 | **atempo 加速** | `MAX_TEMPO = 1.25`；短窗（<1.2 s）`MAX_TEMPO_SHORT = 1.50` | 轻微；>1.55 人耳判"急" |
| 3 | **让翻译引擎按字数预算重写** | 最多 2 轮（`MAX_ROUNDS`） | 会丢意思（见 §3 第 3 条） |
| 4 | 放弃，**报出来** | — | 留给混音阶段掐尾，并进日志清单 |

两处上限容易被写错：

- **`REWRITE_ABOVE` 故意等于 `MAX_TEMPO`（1.25）**：凡是加速能吸收的溢出，就不要去问翻译引擎——
  问它才是把句子写坏的那一步。
- **短窗阈值 1.2 s 和 1.50× 是一套的。** 短窗里是感叹句（"No!"、"Whoa!"），引擎自身的时长方差比窗口还大
  （节奏模型承诺「不！」0.54 s，实际合成 0.96 s）。人遇到感叹句本来也会念快，半秒足够；
  只调倍数不调阈值，普通从句会被判成感叹句。

## 3. 三个反直觉的点

1. **先借静音，再加速。** 这两个顺序反过也可以"跑通"，但把句子往前挪进前一位说话人留下的空隙，
   听众完全听不出来；同样的时间靠 atempo 挣，就听得出来。代码注释里写反过一版，实际行为也跟着反了。
2. **裁静音不是美化，是预算。** 「哇！」曾经合成出 1.68 s（一个字），拟合阶段于是花了整个窗口去加速一段静音，
   混音阶段只好把这句话截短。裁掉两端死气之后，同样的句子直接装进窗口。
3. **重写一定会吃掉意思。** 让翻译引擎"用 8 个字重说这句"，它会删掉看起来次要的从句：
   `All right, fine. I'm freaked out.` 被压成「没事，没关系。」——"我有点害怕了"整句没了，只为了省 1 s。
   反向也有：`Get her coming, we have two minutes left.` 上一轮被压成「快叫她来，只剩两分钟。」，
   这一轮用回完整译法反而更准。**所以重写必须是最后一档，且要人耳抽查。**

## 4. 覆盖表（`zh_overrides.json`）

```json
{ "3": "你有你的机器人，我只想在太空闪耀。", "25": "走走走！", "60": null }
```

- 键是行的 `index`（不是数组下标），值是**要替换的译文**；值是 `null` 表示**这一句整句不配**。
- 三种非它不可的场合：
  - **两句共用一段语音**：转写器把 `You forgot me on Earth!` 和 `I know.` 标在同一段（377.3 s）。
    两句都配，就会为了给后一句腾地方把前一句截成两半——所以后一句置 `null`，保留原声。
  - **短感叹句塞不进去**：`Go, go, go.` 直译「出发，出发，出发。」ratio 2.27，永不进窗；
    换成「走走走！」ratio 1.00。中文口语本来的说法，比强行加速靠谱。
  - **专名/习语**：`And a dick.` 直译「以及一个。」——改成「而且还是个混蛋。」
- 覆盖表要能**活过重跑**（`--from fit` 不覆盖它），否则每次调参都要重打一遍。
- 除此之外还有一张 `GLOSSARY` 做机械替换（`凯莉/西莉亚 → 塞莉亚`）：同一个名字在不同翻译轮次里会被译成不同写法。

## 5. 声线：只允许否决，不允许指认

`step1` 用 ECAPA 嵌入 + 余弦对每个声线中心做归属，要求 0.15 的余量。**70 句里有 29 句达不到这个余量**，
全是 0.4~1.0 s 的短感叹（"Now."、"Be honest."、"Be tender."）：ECAPA 在这种长度上绝对余弦掉到 **0.03~0.17**，
胜者由噪声决定。其中 4 句被判成女主，而画面里是男人在跟机器人说话——成品里听得出来。

补救用的是**基频否决**（parselmouth/Praat 自相关 `to_pitch_ac`，双频带覆盖率）：

| 声源 | 165–350 Hz 有声覆盖率 |
|---|---|
| tom（男，有真值的行） | 0.14 – 0.31 |
| celia（女，有真值的行） | 0.63 – 0.88 |
| 出问题的那段（232–248 s） | 0.00 – 0.37 |

- **单边否决**：`hi_coverage < 0.40` ⇒ 这个声音不可能是女主 ⇒ 只能是男声。
  反过来不成立（两个男声频带重叠），所以它**永远不会"指认"**某个声音是谁，只能否决。
- **按"场"判，不按句判**：同一场对话里声线连续（`TURN_GAP = 6.0 s` 之内算同一场），
  一句长度不够不足以判，一场就够。
- **`unknown` 标签绝不能"借给句数最多的声线"。** 兜底策略曾这么干，而句数最多的是 celia，
  于是 15 句短感叹全变女声——这就是"4:00 男人说话却是女声"的根因。宁可留 `unknown` 用中性处理。

## 6. 混音（`step13`）的三件套

1. **两句话撞在一起是唯一不可接受的缺陷**（背景音乐里藏不住，听众立刻察觉）。
   处理顺序固定：先加速（上限 `HARD_TEMPO = 1.35`，比拟合阶段的 1.25 高一档，因为此时没有别的选择），
   还不行才**掐尾**，并且掐尾的句子要进清单打印出来。行间至少留 `MIN_GAP = 0.03 s`。
2. **没配上中文的行必须补回原声**，否则画面上嘴在动、声音是空的（人声轨已经被整条挖掉）。
   **只能逐行补**：拿人声轨扫"未被覆盖的语音段"会把每句的尾巴都当漏配，
   实测这样往一条 12 分钟中文轨里灌了 60 s 英文。
3. **bed 只在该响的地方压**：基线 `GAIN_BACKING = 0.85`（相对等响的 mono 和），
   有中文行的地方再压 **−3 dB**，边缘 **150 ms 斜坡**（否则每次闪避都"咔"一声）；
   逐句增益对齐到中位数，钳在 ±12 dB；整轨峰值归一到 0.95 再编码。

## 7. 实测基线（照抄对照用）

Tears of Steel 734 s / 71 句，同一份素材、同一台机器：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 超窗句数 | 6（最高 ratio 2.27） | **0** |
| 被掐尾 | 7 | **3**（#17 / #54 / #55） |
| 需要 atempo | 15 句 | **6 句** |
| fit 阶段耗时 | 410.7 s | 358.6 s |
| 混音耗时 | 17.1 s | 18.0 s |

**"0 超窗"不等于"0 缺陷"**：仍有 3 句被混音掐尾（#17 的窗口只有 0.50 s，任何一句中文都装不下）。
验收时两个数都要看，只报"超窗 0"会把问题藏起来。

## 8. 别照抄的旧结论

`deliverables/dubbing-pipeline-方案.md` §13.3 与 `tts-engine-recommendation.md` §11 是实验早/中期的快照，
和实测冲突的地方以本文为准：

| 旧文档说 | 实测 |
|---|---|
| 溢出只用外部 atempo，**上限 1.20** | 1.25；短窗 1.50（§2） |
| 合成 `do_sample=False`、固定种子 | 实际用的 llama-tts 是 `--temp 0.7` 采样：**同一句两次时长不同，超窗集合每轮都会变**。所以不能拿一轮的清单当结论 |
| 引擎定案 XTTS-v2 | 产出 `tears_of_steel_zh_20mb_v2/v3.mp4` 的是 **llama-tts + Qwen3-TTS-12Hz-1.7B-Base Q4_K_M**（+ `mmproj-…Q8_0`）。XTTS 只在 `ab_refs/xtts_*.wav` 留下过试听片段 |
| 模型只用 atempo 就够 | 还需要 §1 的窗口定义、§2 的顺序、§4 的覆盖表 |

因为 TTS 是随机采样，**同一份译文重跑两次，超窗的句子不是同一批**。
调参时不要用"上次那 6 句"当固定靶子，要跑两三轮看集合是否收敛。
