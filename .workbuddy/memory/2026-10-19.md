## 分析：FSR4 / 神经渲染 的引导输入（jitter·depth·motion·exposure）可行性

用户问：神经 NVIDIA 的深度与运动矢量是真算的，FSR4 与神经 AMD 能否也用真算？
以及曝光能否像神经 NVIDIA 一样走默认？

结论（基于源码逐条核实，未改代码）：

### 1. FSR4 用真算 —— 差的是"接线"，不是"数据"
- 数据已经存在于 renderer，两条路径都有：
  - NVOFA（`m_nvof.Flow()`）→ `NvofResolveShader.h` → `m_motion`（R16G16_FLOAT, renderW×H）
  - 分析网格 → `PSExpandGuides`（`:894`）→ 同一张 `m_motion`
  - 深度：`PSWriteDepth`（`:1661-1665`）写 `m_depth`（R32_TYPELESS / D32 DSV + R32 SRV）
- 但 `FsrUpscaleBackend` 的 `CreateGuides`（`FsrUpscaleBackend.cpp:270`）**自建**三张常量纹理
  （depth R32F 全1.0 / motion R16G16F 全0 / exposure 1×1=1.0），`Dispatch` 只吃 `color`+`output`
  两个参数（`FsrUpscaleBackend.cpp:399-400`）→ 引导根本没有接口可传。
- **结论：技术上可行且改动不大**（给 Dispatch 加 depth/motion/exposure 三个参数，改绑 renderer
  的 mr_motion / m_depth）。但必须解决三件事：
  1. 时域历史污染：`PLAN-generated-frame-fsr4-upscale.md` 的上下文#2 是恒 reset 的；源帧上下文
     一旦有真运动+MOV 抵消，历史才会真正参与 —— 这既是收益来源也是鬼影来源。
  2. **格式/单位契约**：常量路径可以把 D32 SRV 当 R32 读（全 1.0 无解读歧义），真实深度 proxy
     的值有语义，FSR 期望的是 HW 深度约定；这个映射未经验证。
  3. cache/key：引导来源改变画面 → 必须进 key。
- **真正的门槛是收益归属**：NVIDIA 侧深度 proxy 的 A/B 结论是"通道活着、几乎零成本、
  但可见收益为零"（`docs/measurements/depth-ab-20260914/REPORT.md`）。FSR4 拿到同样的 proxy，
  没有理由比这个结论更好。

### 2. 神经 AMD 用真算 —— 数据通、但已被有意识地拒绝
- ABI 完全支持，且 runtime 要的就是**真实**运动+深度（`AmdLmxxfApi.h` 门禁清单）。
- 数据源：`motionGuideDirectory`/`depthGuideDirectory` 走 `GuideFiles.h`（PFM，benchmark 的
  `--guide-dump` 产物），这是**唯一已"完全打通"的真实引导路径**（集成方案 §5.3 run 5/7）。
- **代码里有意拒绝**：`OfflineNeuralRenderer.cpp:3810-3812` —— 传 `--motion-source cpu` 时 AMD 直接
  返回 `NeuralRenderFailure::Protocol`："The AMD backend has no CPU block matcher"。
  同处 `:3813-3818` 还拒绝 `--guide-dump`（"consumes guides rather than producing them"）
  与 `--zero-motion-test`。
- 所以"能否真算"的答案是：**能，但要先把这条拒绝撤掉**（P2 计划项）。根因是 `TemporalGuideGenerator`
  只接在 NVIDIA 适配器上（`RunAmdJob` 没接），不是缺能力。
- **但收益已量过且不够**：runtime 自身时域模型融合权重仅 0.081（噪声标准差降 7.8%），
  且前提是引导全对；isotropic 结论是"不在 runtime 层做时域"，改走宿主侧运动补偿累积
  （`TemporalStabilityPolicy.h`），而后者**零运动场就能跑**（信任门判在源帧上）。
  → 真运动场对 AMD 的边际价值主要在 P2 及 `flickerAdded` 可读性，不在画质。

### 3. 曝光走"默认" —— NVIDIA 的"默认"是 AutoExposure，AMD 侧目前反而是常数 1.0
> **【12:27 修正】** 下列"runtime 源码不在仓库里"的推断**已被推翻**。runtime 源码在
> `/Users/qitmac001356/CLionProjects/dlss5-on-amd-9070xt-porting`（上游 checkout
> a9b7a521 / on_amd，其 include/LmxxfNrApi.h 是 **ABI 1**，但带一整套曝光实验补丁）。
> 修正后的结论见文末"曝光路径重新评估"一节。

- NVIDIA 默认 = AutoExposure（`DLSSBackend.cpp:254-257`：`m_exposure ? 0 : AutoExposure`），
  即**不提供曝光纹理**，让 runtime 自己计量。供给曝光实测无效（全真实素材逐位相同），默认关。
- AMD 现状：`MakeFrameInfo`（`AmdLmxxfApi.h:212`）把 `exposure` 留**未设**、`pre_exposure=1`、
  `exposure_scale=1`，且**从不设** `LMXXF_NR_FRAME_FLAG_AUTO_EXPOSURE`
  （全仓 grep：`src/ tests/ tools/` 零引用）。后果是走"无曝光输入"分支：runtime 只有在
  AUTO_EXPOSURE flag 下才自己计量；无 flag 又无纹理 → 这个 SDR 视频路径大概率**根本不做曝光归一**。
- **所以"像 NVIDIA 一样走默认" = 给 AMD 加 `LMXXF_NR_FRAME_FLAG_AUTO_EXPOSURE`**：
  这是最小的改动，且是 ABI 明确支持的路径（"the runtime meters the colour input itself"）。
  `exposure` 留 null 正是文档说的"no usable exposure in this frame"。
- 另需注意：NVIDIA 的 AutoExposure 与"过曝后慢恢复"的报告有关联（`ExposurePolicy.h:10-13` 引
  OptiScaler-DLSSNR PR #77 白点漂移），所以加 flag 前应在 AMD 上做 A/B，并进 cache key。

### 未做
本次纯分析，未修改任何代码。三条建议的落地顺序见回复正文。

## 曝光路径重新评估（12:27，runtime 源码到手后）

源码位置：`/Users/qitmac001356/CLionProjects/dlss5-on-amd-9070xt-porting`
（HEAD `a9b7a521` on_amd；`include/LmxxfNrApi.h` 只有 **ABI 1**，21 个函数指针的 ABI 3
表不在这里 —— 该仓库是**上游移植工程**，不是播放器用的那个 runtime 包。）

### 推翻的推断
上次说"没 flag 又没纹理 → 大概率根本不做曝光归一"。**错。**
runtime 的 codec 有一条**自估白点**路径，且不依赖任何 flag：

- `shaders/native_codec_encode.hlsl:54-62` / `native_codec_decode.hlsl:44-50` 的
  `EffectivePaperWhite()`，无曝光纹理时三分支：
  1. `Reserved.x & 0x10000` → `WhitePointForMean(SampleMeanLuma()) * PaperWhiteScale`
     —— **5×5 采样均亮度自估白点**，这就是 runtime 侧的"自动曝光"。
  2. `Reserved.x & 0x20000` 且 `pre_exposure != 1` → `PaperWhiteScale * pre`
  3. 否则 → `PaperWhiteScale`（常数，**什么都不做**）
- 这三个 bit 由宿主 `NativeCodecParameters` 决定（`src/native_game_codec.h:19-24`）：
  `auto_white`(0x10000) / `use_pre_exposure`(0x20000) / `hue_safe`(0x40000)，
  在 `Record()` 里打包进 `words[17]`（`native_game_codec.h:178`）。
- **关键：三个开关默认全 false**，且 `NativeGameCodec` 才是真实路径（`NATIVE_CODEC_EXPOSURE`
  宏在 shader 里默认 0，那条 `GameExposure.Load()` 分支是**编译期关掉**的）。
- 另注意：`PaperWhiteScale` 只在 `HdrMode == 1` 时被真正使用；`HdrMode != 1` 直接输出 0
  （encode `:109`、decode `:191`）。所以整条白点/曝光链是**HDR 专用**，SDR 视频路径不走它。

→ 修正：AMD 侧不是"缺曝光归一"，而是**缺一个选择**。默认那支 `PaperWhiteScale` 常数
  恰好等于"不做归一"，而 `auto_white` 那支就是现成的自估曝光，只是没被打开。

### 曝光接通后确实有效（RE9 实测，`Development/RE9/presr/`）
- 问题是**已观测的**，不是主观判断。`colour-investigation.md:20` 记录首帧抓取
  （239587750）：输入 RGB9E5 中位 1.457 / P90 5.3125 / max 708，
  **proxy 与 neural 各有 ~58.7% / 59.5% 像素三通道 >0.98（饱和）**。
  `results/exposure/before-game.json` 可复核：`near_white_pixel_fraction`
  = 0.5866（proxy）/ 0.6038（input）。
- 接通曝光后（capture 240239156）：**proxy 饱和率 58.66% → 0.0853%，neural 59.52% → 0.0432%**
  —— 三个数量级。这是"缺归一"造成过曝的直接证据。
  （`before-game.json` / `after-game.json`；两帧不同菜单画面，非像素对齐 A/B。）
- 受控等价性（`results/exposure/validation.txt`）：合成 RGB9E5(.25,.5,.75)，
  输入 ×32 + 曝光 ÷32 → proxy、neural **逐位相同**，最终 RGB **精确 ×32**，alpha 不变；
  旧无曝光 codec 与 613c278 参考 24 次比较 diff=0，12 次 debug view 通过。
- ABI 代价：`LmxxfNrApi.h.patch` 把 `LMXXF_NR_ABI_VERSION` 1→2，
  `LmxxfNrFrameInfo` 追加 `exposure / exposure_state / pre_exposure / exposure_scale`。
  宿主与 runtime 必须同时重建。播放器的 ABI 3 头里这几个字段**已经存在**
  （`third_party/lmxxf/LmxxfNrApi.h:140-148`），位置一致。
- 已知风险（`colour-investigation.md:22`）：曝光资源换指针时保守 drain 并重建链，
  游戏频繁轮换会有额外成本。

### 对播放器的含义（修正）
> **【12:53 二次修正 — RE9 作废】用户明确要求：RE9 是游戏引擎路径，排除，不要参考。**

## 介入影响分析（13:51）——AMD 真引导 / FSR4 真引导

### 先修正一处事实：AMD 真引导不是"没接"，是"已接、只喂常量"
- `AmdLmxxfEvaluator.cpp:1846-1864`：`UploadGuides()` 每帧上传，构造 `TemporalGuides`
  （motion `R32G32_FLOAT` 全帧 / depth `R32_FLOAT` 全帧，`motionScaleX/Y = width_/height_`，
  `jitter=0`），`guides.flags = kTemporalVideoFlags`（含 MODEL_HISTORY|INPUTS_VALID|MV_JITTERED），
  `guides.reset = resetRequested`，然后 `ApplyTemporalGuides(frameInfo, guides)`。
- `leases_ = config_.temporalHistory`（`:701`），开则 `CreateSession` 带
  `LMXXF_NR_CREATE_FLAG_RECORDING_LEASES`，走 `SubmitFrameLease`（`:2001`）。
- `CreateGuideTextures`（`:387-430`）注释：全帧而非 160×90 分析网格，理由是要 scale=1、
  避免"在未校准量上再叠一个未知"；文件源也会 `ResampleArea` 到全帧再喂。
→ 所以 `OfflineNeuralRenderer.cpp:3810-3818` 那三条拒绝只是 **benchmark 开关**的拒绝
（cpu 运动源 / guide-dump / zero-motion-test），**不是产品路径没接**。产品要真运动，
缺的是"实时运动估计器 → UploadGuides"这一段，AMD 上没有 NVOFA。

### 收益（都是小的，且多半已被量过）
1. runtime 时域模型从假引导变真引导：上限就是 **融合权重 0.081 / 噪声 std 上限降 7.8%**
   （引导全对时测的），这是天花板不是增量。
2. `flickerAdded`/warp 指标变准：现在零矢量 = 不补偿的逐帧差（`TemporalMetrics.h:255`），
   运动区会误报。真运动让指标可信 —— **决策质量收益，非画质收益**。
3. 深度给 runtime 做 disocclusion 判定：但 proxy 是亮度/运动/梯度启发式，非几何；
   NVIDIA 侧同源 A/B 结论"通道活着、近乎零成本、可见收益为零"（depth-ab-20260914）。
4. 实验能力（benchmark 能用 cpu 运动源、能 dump 引导）—— 工程收益。

### 负面（按严重度）
1. **精度错配**：CPU 块匹配是 160×90 分析网格，上采样到全帧喂逐像素 MV 语义的输入。
   硬证据反证：`neural-mv-gate-20260924` 在视频上 A/B 出"零运动反而更好"
   （still-hold sigma 0.439→0.366、PSNR 36.34→36.50；real-game-motion flicker 0.306→0.243）。
   → 视频的运动场质量压不住重投影。
2. **双层时域串联**：宿主 P2.5 累积已在跑（静止段抖动 −28.5/−45.7/−62.3% Low/Medium/High，
   离源仅 0.1 dB），runtime 历史再叠一层 → 两个递归滤波串联，时间常数相加，转场/大运动后
   恢复变慢、拖尾。当前"常量引导 + 宿主累积"实际是单层，接真运动后变双层。
3. **reset 契约负担**：`guides.reset` 必须每帧判对（seek/cut/drop/换源）。视频切镜频率
   远高于游戏，漏判即把前镜头抹进后镜头（注释原话 "silently smears"）。
4. **静默降级**：任一门禁不过 → 整帧退空域，不报错，只写 historyStatus。部分帧成功/
   部分失败 → 累积状态跳变 → 闪烁，且比"一直关"更难诊断。
5. **带宽**：motion+depth 全帧 = 1920×1080×(8+4)B ≈ 24 MB/帧 ≈ 1.4 GB/s @60fps，
   外加文件源的 ResampleArea。不是免费的。
6. **回归面**：画面变化 → cache key 全失效；历史测量数据不可比。

### FSR4 接真引导
- 收益：重投影从恒等变真值，运动物体的历史可复用 → 细节稳定性。
- 结构天花板：**jitter 仍为 0**。FSR4 时域超分靠 jitter 积累亚像素采样；没有 jitter，
  历史只能去噪/稳边，不能重建细节。而给解码帧加 jitter 又需要重投影补偿，采样网格固定
  → 可见 wobble（`FsrUpscaleBackend.h:13-30` 已把这条写死为设计理由）。
- 负面：字幕/水印/UI 鬼影——FSR4 的 reactive / transparencyAndComposition 是 OPTIONAL
  （`FsrUpscaleAbi.h:174-185`），视频没有 mask 可给，静态叠加层会被当背景重投影；
  depth proxy 误判前景/背景；块匹配在压缩噪声上产假运动
  （false mv: real-game-motion 0.0647、depth-pan 0.1773）→ 历史错位。

### 净判断
两条都是"收益已量过且很小 + 负面静默且难诊断"。AMD 侧宿主累积已经在拿主要收益，
runtime 真引导的边际被 0.081 封顶；FSR4 侧 jitter=0 是结构性天花板。
→ 建议：不做默认路径；最多做实验开关（benchmark 可跑），且必须进 cache key。

本次仍为分析，未改代码。

## 为什么 NVIDIA 没这个问题（14:00 追查）+ 上一轮一处过度归因的修正

### 根因：运动场精度差一个数量级（硬差距，非实现差异）
- NVOFA：`OpticalFlowNvof.cpp:155-160` 选 **grid 2**（每 2×2 像素一个矢量），
  1080p → 960×540 矢量场。注释原话："One vector per 2x2 pixels is still a
  **twelvefold refinement on the CPU estimator's 24×24 block at 1080p**"。
  grid 1 实测帧循环 17.2 ms vs 8.9 ms，所以没用最细的。
- CPU 块匹配：`TemporalGuides.cpp:93` `gw = clamp(sourceW/divisor, 96, maxGridW)`，
  divisor 10（<45fps）/14（≥45fps），maxGridW 160/128 → 1080p/30fps = 160×90（约 12px 块），
  60fps = 128×72（约 15px 块）。**GPU 再 expand 到全帧，精度不会因此变高。**
- AMD 上 NVOFA 不可用（NVIDIA 私有 API），`PlanHardwareFlow` refusal →
  只能吃 160×90/128×72 的场。

### 第二差异：NVIDIA 有两道补偿，AMD 都缺
1. **zero-motion test**（`D3D12Renderer.cpp:1645` `m_preserveSource||m_zeroMotionTest`，
   resolve shader 第 8 个 root constant）：专修"固定帧 NVOFA 仍报非零场"。
   实测 still-hold sigma 0.439→0.366、PSNR 36.34→36.50，且进 cache key（`|mv-zero-test-v1`）。
   AMD 侧对应开关 `--zero-motion-test` 被直接拒绝（`OfflineNeuralRenderer.cpp:3818`），
   因为 "the AMD backend does not run the neural motion policy"。
2. **三级渐进降级**：NVOFA → CPU 网格 → 零，每级都合法可用。
   AMD 是二值：真值 or 常量，且门禁失败**静默**退空域。

### 【修正】"双层时域串联"不是 AMD 独有，我上一轮归因过度
- `DLSSBackend.cpp:337-343` jitter 同样钉 0、MV scale 1，NVIDIA runtime 时域也在跑；
  宿主 P2.5 累积同样在 NVIDIA capture 路径之后。→ **两边都是双层。**
- 真正的差别在权重：AMD runtime 融合权重实测 **0.081**（只用 8% 历史），
  所以它叠加到宿主累积上的复合效应**被自身低权重限制住**，不是"严重拖尾"。
- 修正后的严重度：双层 → **轻微但同向**（都往历史拉，转场恢复略慢）。
  真正站得住的负面是精度错配（6–12 倍线性）、固定帧假运动无补偿、以及静默降级。

### AMD 能参考解决什么
能：
1. **搬 zero-motion test**：纯宿主侧，在 `UploadGuides` 前判"两帧相同 → 场置零"，
   不需要 runtime 支持。最直接可抄的一条。
2. **搬渐进降级**：把"网格 → 零"做成显式档位 + 进 cache key，而不是门禁失败静默。
3. **搬可见性**：把 `historyStatus` 从日志提升进收据/render report。
4. **提网格精度**：divisor 10→8、maxGridW 160→240 之类，代价是 CPU 时间（需实测）。
不能：
- NVOFA（NVIDIA 私有 NV_OF API，AMD 无等价公开接口）→ 2×2 质量档拿不到。
结论：AMD 只能补**补偿层**，补不了**数据层**。策略应是"承认精度低 → runtime 时域保持关，
时域收益全部交给宿主累积"，这恰好就是当前架构。

## 替代 NVOFA 的方案：FidelityFX Optical Flow（14:06 调研，未改代码）

### 结论：有，而且已经在另一个工程里做成生产默认
`/Users/qitmac001356/CLionProjects/dlss5-neural-amd`（分支 on_amd，v0.7.12）内含**完整**的
AMD FidelityFX Optical Flow 实现，自 v0.7.1（2026-09-28）起是"游戏不给矢量时"的**默认运动源**。

| 件 | 位置 | 说明 |
|---|---|---|
| 编译开关 | `core/temporal/ffx.h` | `AMDNR_WITH_FFX`；`build.ps1 -Ffx <SDK>` |
| 实现 | `core/temporal/optical_flow.inc`（255 行） | 参考 Magpie `AmdOpticalFlowProvider.cpp` |
| shader 生成 | `tools/gen_ffx_opticalflow.ps1` | 7 个 pass 用 dxc 编成 permutation header |
| 强制项 | `tools/release-assets.ps1` | 拒绝不带光流的 `amd-nr.addon64` |
| SDK | AMD FSR SDK 2.3.0，MIT（`docs/third-party/fidelityfx-LICENSE.md`） | 跨厂商，D3D12 有官方 backend |

**技术参数**（`optical_flow.inc:1-10,120-230`）：
- 输入：原尺寸（Quality，**不下采样**）8-bit RGBA，`FFX_API_BACKBUFFER_TRANSFER_FUNCTION_SRGB`，
  `minMaxLuminance {0,1}`；sparse 矢量 `R16G16_SINT`，8×8 块
- 7 pass：prepare_luma / luminance_pyramid / optical_flow_advanced_v5 / filter_v5 /
  scd_histogram / scd_divergence / scale_flow_v5
- 输出：稀疏场 → `kFlowDensifyShader` densify 到全帧 `R16G16_FLOAT`，**按深度加权**
  （8×8 块跨轮廓时，纯双线性会把矢量糊 8–16px 到边界两侧；深度加权后 10% 相对差保留半权重）
- 1080p 下场 = 240×135

### 【重要修正】根因不是"精度差 12 倍"，是"场的自洽性"
CHANGELOG v0.7.1 原话（决定性）：
> The estimator matched nine samples of a frame shrunk to an eighth, one sample per 8x8 block,
> so on a textured scene a camera pan came out as noise -- **neighbouring blocks pointing opposite
> ways. The runtime, handed motion that did not line its history up with the picture, dropped the
> history**: the effect faded and flickered while the camera moved and came back once it stopped.

→ 块匹配与 FFX OF **同为 8×8 粒度**（`fw = max(16, nw/8)`，`neural.cpp:2009-2010`），
精度一样，但块匹配的场噪声大（相邻块反向）→ runtime 判定不可信 → **丢弃历史**。
FFX OF 靠金字塔 + 鲁棒估计 + 正则化，场自洽 → 历史保住。
**所以上一轮"12 倍精度差是根因"要降级为"表现"，真因是场的可靠性。**

### 已知缺陷与工程对策（都已存在）
1. 切镜后 **6 帧全零**（`real = primed && dispatched >= 6`，SDK 的 IsSceneChanged）→
   当 reset 处理，`g_motionSinceEvaluation = real`。
2. **平坦暗区返回几万像素的垃圾矢量** → `DLSS5_MOTION_MAX_PX`（`native_temporal_feed.h:58`，
   Magpie 路线）把超长矢量当静止。
3. 8×8 块跨轮廓糊 8–16px → densify 按深度加权（无 depth 时退纯双线性）。
4. 32-bit 路线没有光流，保留估计器。

### 两个工程的分工（别搞混）
- `dlss5-neural-amd`：**自己算光流**（FFX OF 完整实现），ReShade add-on 路线。
- `dlss5-on-amd-9070xt-porting`：**只接收**光流。`src/native_temporal_feed.h` 把 motion texture
  转成 runtime 的 motion buffer（`Create(motion_w, motion_h, pixel_scale_x, pixel_scale_y)`），
  光流由 Magpie 提供。同一份代码也吃 `DLSS5_MOTION_MAX_PX` 钳制。

### 对播放器的可行性
技术上可行（SDK 是 MIT、D3D12、不需要 ReShade），但要付：
1. 集成 FFX SDK + 扩构建链跑 dxc 编 7 个 pass（cs_6_2）；
2. 视频没有可靠 depth → densify 降为纯双线性（参考实现本就如此）；
3. 性能未测（游戏里能跑 ≠ 播放器有余量）；
4. **反向证据**：NVIDIA 的参考实现（RenoDX）在无引擎场景用的是**零运动 + 时域开**，
   不是光流（`docs/nvidia-parity.md:64-78`："ETS2 has no DLSS, so its motion vectors and
   depth were dummies... the DLL did with the dummies"）。即官方对"无引擎"的答案是零运动。

→ 判断：FFX OF 是**真正的技术答案**，但"视频场景下它比零运动更好"这一点**还没有证据**。
应先做离屏 A/B（同一 clip，零运动 vs FFX OF，看 flickerAdded / warp+ / 鬼影），
而不是直接接进产品。
