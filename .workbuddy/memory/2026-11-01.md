# 2026-11-01

## macOS 移植可行性验证（阶段 1 完成）

**背景**：用户问"当前播放器能否移植过来，先移植 UI 和视频播放"。分支 `main-apple` 当时是空的（与 main 无差异），移植未开始。

**关键代码结构发现**（决定了移植成本）：

- 解码**不链接 libav***：`src/VideoDecoder.cpp` spawn `ffmpeg.exe` 子进程，`-f rawvideo pipe:1` 读裸像素（第 1024 行附近拼参数）。音频 `AudioPlayer.cpp` 同样走 ffmpeg 子进程。
- 因此跨平台只需换进程创建方式 + hwaccel 名，解码逻辑零改动。这是移植最大利好。
- `src/main.cpp` 16257 行是单一 `PlayerApp` 类（从 3371 行起），Win32 窗口 + GDI 手画 chrome（305 处 CreateWindowExW/FillRect/DrawTextW/CreateFontW，211 处 WM_*）+ 菜单 + 6 个对话框 + 业务胶水全在一个 TU。UI 是**重写**不是移植。
- 56 个 `*Policy.h` 共 11700 行，其中 11200 行纯逻辑（只用 RECT/COLORREF），可整块搬。
- `D3D12Renderer.cpp` 5875 行里只有约 464 行提及 neural/fsr/dlss（8%），主体是普通呈现路径。
- 构建链硬锁：CMakeLists 开头 FATAL_ERROR 在非 WIN32 / 非 MSVC。

**已验证跑通（mac/src，1430 行，ctest 2/2 通过）**：

| 项 | 结果 |
|---|---|
| ffprobe 解析 | 全对，含 `24000/1001` 分数帧率 |
| ffmpeg 裸流管道 | `-pix_fmt bgra -fps_mode cfr -r <fps> -f rawvideo pipe:1` 逐字节兼容 |
| 帧数一致性 | 640×360/3s/24fps → 72 帧；2118×1046/6s/30fps → 180 帧 |
| seek 精度 | 1.800s → 第 43 帧，误差 0（非关键帧对齐） |
| 解码吞吐 | 640×360: 675fps；2118×1046: 227fps |
| Metal 离屏渲染回读 | 0% 残留清屏色，40015 次颜色跳变 |

**踩到的坑（重要，勿重复）**：

1. `Metal.h` 会拉 Foundation（Objective-C），**不能**在 .cpp 纯 C++ TU 里 `#include`。解决：`MetalVideoPresenter.h` 用 pimpl，layer 以 `void*` 传递，实现在 .mm 里 `(__bridge CAMetalLayer*)`。
2. `posix_spawn` 不走 shell，用 shell 引号拼命令再按空格切分会把引号带进参数导致 ffmpeg 找不到文件（表现为解码出 0 帧）。必须直接构造 argv 数组。ffprobe 走 popen 才有 shell，可以用引号。
3. `CAMetalLayer*` 传给 `void*` 参数需要 `(__bridge void*)`。
4. macOS AppKit 下 screencapture 截不到自绘窗口时，用离屏渲染 + `getBytes` 回读验证像素，比截图可靠（且 System Events 需要辅助功能权限）。

**建议下一步顺序**（已写入 mac/README.md）：
1. 音频 CoreAudio（`WasapiRenderer.cpp` 946 行）—— **先做，它会改变时钟语义，晚做要返工**
2. 搬 Policy 层（RECT/COLORREF → 平台无关类型，一次拿回 11k 行）
3. UI 框架选型：Qt6 / SDL3+ImGui / SwiftUI
4. 字幕（`SubtitleOverlay.cpp` 输出已是预乘 BGRA，与 Metal 纹理同格式，接入成本低）

**明确不做**：不用 AVPlayer（会丢掉渲染缓存/compare views 的核心价值）；现在不碰神经渲染（AMD HIP/Vulkan runtime 在 macOS 无等价物）。

**构建命令**：`cmake -S mac -B mac/build -G Ninja && cmake --build mac/build && ctest --test-dir mac/build`

## 阶段 2：音频（同日完成）

**做了什么**：`AudioPlayer`（ffmpeg 音频子进程 + 主时钟）、`CoreAudioSink`（AudioQueue 输出），并把 `AudioClockPolicy.h` **原样零修改**复制到 mac/src（纯算术，跨平台通用）。

**核心设计决定**：
- **音频是主时钟**。Windows 版 presentation gate 按音频位置决定显示哪帧。自己计时会让画面相对声音漂移（声卡晶振 vs 系统时钟，每几分钟一帧）。`PlaybackClock::Position()` 音频优先、计时器兜底。
- **AudioQueue 而非 AudioUnit**：拿到的是无帧边界字节流，AudioQueue buffer 回调 1:1 映射；AUHAL 还要自己拥有渲染线程和时钟。
- `AudioClockPolicy.h` 的 `Usable`/`Present` 解决"音频位置冻结"（子进程结束/欠载/设备掉线会让位置冻结，而闸门会把画面永久停住）：冻结 >0.5s 按墙钟带前，恢复时 ≤5% 斜率追回，差 >1s 才跳。

**实测数据**：时钟 1.010s 墙钟走 0.994s（误差 -1.6%）；暂停冻结不跑偏；seek 从目标起算；停止报负值回退；音频首帧延迟 338ms。ctest 3/3 绿。

**新踩的坑（重要，勿重复）**：
1. **`Write` 无界等待会死锁**：设备不再要数据时队列回调不触发，读取线程永久阻塞 → `Stop()` 的 join 永远等（实测 SIGTERM）。解决：20ms 超时轮询 + 检查 stop/paused 标志。
2. **暂停后音频自己重启**：写入线程卡在 `Write` 里，`FadeOutAndStop` 停了队列但该线程拿到缓冲区后又 `AudioQueueStart`。解决：`Write` 接受 abort 标志，且在往队列放缓冲区**之前**检查。
3. **`ReaderLoop` 数据竞争**：子线程读 `m_path`/`m_track`，`Seek()` 在主线程重写。解决：参数按值传入线程。
4. CVDisplayLink 在 macOS 15+ 废弃但仍是首选（替代方案走 run loop 会改变帧追赶所在线程），用 `#pragma clang diagnostic` 局部静音。

**当前按键**：空格暂停、`←/→` ±10s、`.` 单帧、`A` fit/fill、`M` 静音。

## 阶段 3：Policy 层移植（同日完成）

**成果**：16441 行移植（`mac/policy/`，77 个头文件），**非 include 的逻辑改动仅 17 行**（只有 `RuntimeModulePolicy.h` 一处）。19 个文件逐字节未改。56 个 policy 中 50 个通过，排除 5 个（AudioEndpoint → IMMNotificationClient COM 接口；AudioPassthrough → IEC61937 GUID；DarkMode → UAHMENU 未文档化协议；NvencDirect → NVENC；RendererRecovery → HWND）。

**方法论**：不重写，建 `UiTypes.h` 兼容层用 `using` 定义 Win32 词汇（RECT/POINT/SIZE/COLORREF/UINT/DWORD/LONG/BOOL + MulDiv/OffsetRect/IntersectRect/swprintf_s/MultiByteToWideChar 等），`PlatformCompat.h` 作为统一入口，每个移植文件只改 include。

**关键语义必须精确匹配**（错一处 UI 就差一像素或颜色互补，且照样能画出来）：
- `RECT` 右/下**开区间**（`right-left` 是宽度）
- `COLORREF` 是 **0x00BBGGRR**
- `MulDiv` **半远离零**舍入（不是截断）
- `InflateRect` 负数收缩

**本阶段踩的坑（重要）**：
1. **`LONG` 必须是 `long` 不是 `int32_t`**。Windows 两者都 4 字节，LP64 上不是。`WindowPlacementPolicy` 用 `%ld` 读写 LONG，varargs 格式必须精确匹配宽度，否则读时从 8 字节槽取 4 字节后面全是垃圾。**宽度跟着格式走，不跟 Windows 结构体走**。
2. **`UINT_MAX`/`LONG_MIN`/`LONG_MAX` 不能自己定义**——`<climits>` 定义成宏，宏赢过 `using` 声明，导致语法错误。
3. **`mbsrtowcs` 不能做 UTF-8 转换**：服从 C locale，GUI 进程启动是 `"C"`，0x80 以上全失败。从 Finder 启动的播放器永不调 setlocale → 只有中文文件名用户会遇到（即绝大多数用户）。改手写 UTF-8 编解码。
4. `to_wstring(cond ? 0 : count())` 在 LP64 有歧义（三元两分支类型不同 → `long`，两个重载都不匹配）。
5. `MTLStorageModeManaged` 是独显概念，Apple Silicon 上无效，macOS 27 已废弃 → 改 `MTLStorageModeShared`（统一内存，还省了 synchronize）。

**ctest 5/5 绿，零警告**。

```bash

/tmp/aqtenv/bin/aqt install-qt mac desktop 6.12.0 clang_64 --outputdir mac/.qt
cmake -S mac -B mac/build -G Ninja -DCMAKE_PREFIX_PATH="$PWD/mac/.qt/6.12.0/macos"
```
`-m qttools` 会超时失败但 qtbase 已装好（播放器只要 Widgets）。`.qt/` 211MB，装到 mac/ 内以便 mac/.gitignore 生效（不改根 .gitignore，遵守"不碰上游"原则）。

**本阶段踩的坑**：
1. **`logicalDotsPerInch()` 不存在于 QPaintDevice**——Qt6 里 QPaintDevice 提供 `logicalDpiX()`/`logicalDpiY()`，`logicalDotsPerInch` 是 QScreen 的属性。全部改用 `logicalDpiX()`。
2. `PlayerWindow.h` 的槽函数参数 `ToolbarAction` 需要 include `UiLayout.h`，否则 moc 生成的代码不认识该类型。
3. 局部变量名 `height` 遮蔽 `QWidget::height()`，导致 `height()` 调用变成"把 double 当函数调"。
4. `QPair` 在 Qt6 已弃用，改 `std::pair`。
5. 宏传字符串给 Qt 要用 `QString::fromUtf8(MACRO)`，不能 `QStringLiteral(MACRO)`。

## 严重 bug 修复：长视频画面静止（用户报告）

**现象**：播放 734 秒的《Tears of Steel》(1920×800/24fps) 画面完全不动；6 秒的测试片正常。

**根因**：`TryPop` 是「取出并删除」，但消费方写成：
```cpp
while (TryPop(candidate)) {
    if (candidate.number > want) break;   // ← 这一帧已经被取出来了，break 就是丢掉
    m_current = std::move(candidate);
}
```
生产者比时钟快，队头几乎总是超前 → 每个 tick 丢一帧 → 画面冻在第一帧，队列被逐帧倒进垃圾桶。

**为什么短测试片没暴露**：6 秒片子整个文件早就解进管道了，竞争在头一秒内就分出胜负；734 秒的片子一直在流式生产，所以稳定触发。**这解释了为什么之前所有自测都是绿的**——测试素材太短。

**修复**：新增 `FfmpegPipeSource::PeekFrontNumber(int64_t&)`（加锁读队头编号，`m_mutex` 改 `mutable`），消费方改成「先 Peek 判断、合适再 Pop」。同时修了 `main.mm` 里同样的 bug（注释还写着 "keep it and stop"，实际上没保住）。

**验证**：修复前 120 tick 只有 2 次更新；修复后 56~57 次，落在第 60 帧（24fps×2s = 48~60）。实际运行《Tears of Steel》截图对比差异 18.26% → 5 秒后仍 19.93%。已在 `PipeSourceTests` 加了 consumer 回归测试（阈值：至少 expected/4 次更新 + 达到目标帧）。

**教训**：所有测试素材都只有 3~6 秒，掩盖了一个只在流式长片下才显现的 bug。测试素材应该包含一个长文件。

**本轮抓到的两个真 bug**：
1. **`Close()` 死锁（严重）**：`m_stop = true` 后没有 `notify_all()`，producer 在 `m_ready.wait(队列满)` 里永远睡着，join 卡死 → **关闭播放器会挂住**。实测 6 秒素材卡 60 秒以上。修复：设标志后立即 notify，再关管道/kill 子进程，最后 join。同时把 `m_pipe`/`m_pid` 用 `m_pipeMutex` 保护（Close 从调用线程访问，producer 从自己线程访问）。
2. **测试自身的采样 bug**：最初采样 y 在 pill 垂直中心，正好是图标位置；且用 `LayoutToolbar(1440,68,96)` 重算坐标而 widget 内部 DPI 不同 → 误报"7 个 pill 只有 4 个画了"。修复：给 ToolbarWidget 加 `items()` getter，测试直接用 widget 真实布局，采样点改到左上角内 4px。
